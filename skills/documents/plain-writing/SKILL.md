# 담백한 문서 쓰기

## 왜 있는가

평가자가 발표 자료를 보고 "AI 로 만들었다"고 지적했다. 감점 사유가 됐다.
내용이 틀려서가 아니었다. 모양과 문장이 AI 가 쓴 글처럼 보였다.

AI 가 쓴 글은 티가 난다. 문장마다 줄표로 설명을 붙인다. 굵은 글씨가 많다.
결론을 한 줄로 요약하고 그 뒤에 이유를 단다. 산출물보다 설명이 많다.

이 스킬은 그런 글을 쓰지 않게 한다.

## 규칙 1. 산출물을 보여 준다

발표와 보고서의 본문은 **실제로 만든 것**이다.

| 넣는다 | 넣지 않는다 |
|---|---|
| 구조도 · 설계도 | 한 일을 나열한 문장 |
| 실제 데이터 · 분석 결과(표·그래프) | 과정 설명 ("~을 검토했습니다") |
| 화면 설계 · 실제 화면 | 관리 지표 (문서 수 · 쪽수 · 결정 건수) |
| DB 스키마 · 실제 행 | 결론을 한 줄로 뽑은 강조 문구 |
| 실행 결과 · 테스트 결과 | 청중에게 묻는 질문 |

그림 한 장이 문단 하나보다 낫다. 그림 옆 글은 두세 줄로 끝낸다.

## 규칙 2. 주어진 양식을 따른다

- 기관이 준 양식이 있으면 그 파일에 채운다. 새로 디자인하지 않는다.
- 양식이 없으면 **직전 회차 최종본**을 연다. 그 구조와 서식을 그대로 쓴다.
- 초안이 아니라 **최종본**이 기준이다. 사람이 고친 흔적이 규칙이다.
- 양식이 정한 형식은 이 스킬의 규칙보다 우선한다. 양식이 `o 항목 (설명)`, `1단계 : 설계`, `용어 : 설명` 으로
  쓰고 있으면 그대로 따른다. 검사 스크립트가 이것을 콜론 설명으로 잡아도 고치지 않는다.
- 장식을 더하지 않는다. 아이콘 · 이모지 · 그라데이션 · 카드 남발을 피한다.
- 사용자가 결과물을 직접 고쳤으면 그 판이 정본이다. 다음 판은 고친 곳을 되살려 만든다.

## 규칙 3. 문장은 짧고 단순하게

- 한 문장에 한 가지만 말한다.
- 문장은 40자 안팎에서 끊는다.
- 주어와 서술어를 분명히 쓴다.
- 명사로 끝나는 개조식과 서술형을 한 목록 안에서 섞지 않는다.

### 🔴 금지 — "내용 - 부연설명" 형식

제목이나 항목 뒤에 줄표를 붙이고 설명을 잇지 않는다. 줄표의 종류와 상관없다.

```
금지   서버 구성 — 웹·API 서버 1개
금지   배치 확정 - 서버는 사내 VM
금지   특장점: 본문을 서버에 두지 않는다 (용량 절약)
```

```
허용   서버는 웹·API 서버 하나로 구성한다.
허용   서버는 사내 VM 에 둔다.
허용   대화 본문은 서버에 두지 않는다. 서버 용량을 아끼기 위해서다.
```

설명이 필요하면 **문장을 하나 더 쓴다.** 괄호로 덧붙이지도 않는다.

### AI 티가 나는 표현

| 피한다 | 대신 |
|---|---|
| 줄표(—, –, -)로 설명 잇기 | 문장을 나눈다 |
| "A 가 아니라 B 다" 대구 | "B 다" |
| "핵심은 ~", "즉 ~", "결론적으로 ~" | 그냥 말한다 |
| 한 문단에 굵은 글씨 여러 개 | 굵게 쓰지 않는다. 꼭 필요하면 문서 전체에 몇 곳만 |
| 화살표(→)로 문장 잇기 | 동사를 쓴다 |
| 세 개씩 짝지은 나열 반복 | 필요한 만큼만 쓴다 |
| 따옴표로 강조 | 따옴표는 인용에만 |
| "~하는 것이 중요합니다" 남발 | 사실만 쓴다 |
| "~할 수 있습니다" 남발 | 사실이면 단정한다. 가능성이면 남긴다. 아래 "고칠 때 지킬 것" |
| "시사하는 바가 크다", "주목할 만하다", "매우 중요하다" | 지운다. 남길 거면 구체 근거를 쓴다 |
| "다음과 같다", "크게 세 가지로 나눌 수 있다" 도입 | 도입구를 지우고 바로 쓴다 |
| "문제는 ~", "관건은 ~", "필요한 것은 ~이다" | 주어와 서술어를 바로 잇는다. "방향이 필요하다" |
| "~하는 이유다", "~할 때입니다", "~다는 것이다" 로 끝맺기 | "그래서 ~다", "~다" 로 끝낸다 |
| "단순한 X 를 넘어 Y", "X 에서 Y 로" 변환 공식 | 바뀐 것을 그냥 쓴다 |
| 연결어미 뒤 쉼표 ("만들고, 나누며,") | 쉼표를 뺀다 |
| 모든 항목 끝에 이유 달기 | 이유는 질문받을 곳에만 |
| 슬라이드마다 한 줄 요약 문구 | 제목으로 충분하다 |
| 절마다 같은 소제목 틀 반복 (요약 · 옵션 · 제안 등) | 끝의 결론 절 한 곳에 모은다. 본문 절은 표와 추천 한두 문장으로 닫는다 |
| 두 가지로 읽히는 괄호 (`2차 표시 없애기(운영자 제외)`) | 빼는지 남기는지 문장으로 쓴다 |

마지막 두 줄은 실제로 지적받은 것이다. 절마다 요약·옵션·제안을 달았더니 난잡하다고 했다.
괄호 속 `제외` 는 쓴 사람과 읽은 사람이 반대로 이해해 두 판을 다시 만들었다.

### 번역투

한국어 AI 글의 티는 대부분 영어를 옮긴 말투에서 나온다.

| 피한다 | 대신 |
|---|---|
| X 에 있어서 | X 에서 |
| X 를 통해 Y 한다 | X 로 Y 한다 |
| X 에 대해 논의한다 (한 문단에 여러 번) | X 를 논의한다 |
| X 와 관련하여, X 에 관하여 | X 에, X 의 |
| X 에 기반하여, X 를 바탕으로 (남발) | X 로, X 를 보고 |
| X 를 위해 Y 한다 (남발) | X 하려고, X 하도록 |
| 경쟁력을 가지고 있다 | 경쟁력이 있다 |
| 회의를 가졌다, 합의가 이루어졌다 | 회의를 했다, 합의했다 |
| AI 에 의해 생성된 | AI 가 만든 |
| 판단되어진다, 쓰여지게 된다 | 판단된다, 쓰인다 |
| 서버에서의 처리, 웹으로의 전환 | 서버가 처리한다, 웹으로 바꾼다 |
| 같은 "~되고 있다" 가 한 문단에 셋 이상 | 몇 개는 "~됐다", "~한다" 로 |
| 한글 뒤 영어 괄호를 매번 (`허브(Hub)`) | 처음 한 번만 병기한다 |

"~의" 하나는 번역투가 아니다. 업계 표준 용어(API, DB, 토큰)는 우리말로 옮기지 않는다.

## 규칙 4. 발표 자료는 그림이 본문이다

- 한 장에 한 메시지. 제목과 소제목만 읽어도 흐름이 보이게 한다.
- 그림 · 사진 · 그래프 · 실제 화면을 많이 넣는다. 글은 짧은 단문으로, 한 줄 15자 안팎.
- 긴 문단은 결론 한 줄과 근거 두세 개, 시각자료 하나로 바꾼다.
- 잰 값이 없으면 숫자를 만들지 않는다. 양식의 예시 그래프와 예시 수치는 지운다.
- 요청에서 뺀 항목은 목차와 본문에서 모두 뺀다.

## 고칠 때 지킬 것

이미 쓴 글을 다듬을 때는 문체만 바꾼다. 내용이 바뀌면 고친 것이 아니라 다른 글이다.

- 고유명사 · 수치 · 날짜 · 단위 · 인용은 한 글자도 바꾸지 않는다.
- 문장마다 핵심 명사를 먼저 짚는다. 고친 뒤에도 그 말이 남아 있어야 한다. 빠졌으면 되돌린다.
- 주장의 강도를 바꾸지 않는다. "~해야 한다" 를 "~한다" 로, "~일 수 있다" 를 "~이다" 로 올리지 않는다.
  겹친 완곡("~할 수 있을 것으로 보인다")만 하나로 줄인다("~로 보인다").
- 빼는 방향으로만 고친다. 원문에 없던 비유 · 상투어 · 결말 문장("~하는 이유다")을 새로 넣지 않는다.
- 걸린 곳만 고친다. 문단을 통째로 다시 쓰지 않는다. 문장 절반 이상이 바뀌었으면 내용이 상했는지 의심한다.
- 말투 등급을 지킨다. 합쇼체는 합쇼체로, 한다체는 한다체로. "했다" 를 "하였다" 로 올리지 않는다.
- 대구 · 반복을 전부 없애지 않는다. 연달아 몰린 것만 풀고 한두 개는 남긴다.

다 고치면 원문과 나란히 놓고 위 항목을 다시 본다.

humanize-korean 에서 가져오지 않은 것이 둘 있다. 불릿을 산문으로 바꾸기와 일부러 긴 문장 섞기다.
제출물은 양식이 개조식을 정하고(규칙 2), 이 스킬은 짧은 문장을 쓴다(규칙 3).

## 쓰는 순서

1. 양식이나 직전 최종본을 연다.
2. 넣을 산출물(그림·표·데이터)을 먼저 고른다.
3. 산출물마다 제목과 짧은 설명 두세 줄을 붙인다.
4. `scripts/check_tone.py` 로 검사한다.
5. 걸린 문장을 고친다. 줄표를 괄호로 바꾸는 것은 고친 것이 아니다.
6. 스크립트가 못 잡는 것을 눈으로 본다. 괄호 덧붙임, 절마다 반복되는 틀, 산출물 없이 설명만 있는 장.

## 검사 스크립트

```bash
python scripts/check_tone.py <파일 또는 폴더> [...]
```

- `.md` `.txt` `.docx` `.pptx` `.hwpx` 를 읽는다.
- 설치할 것이 없다(bootstrap 불필요). Python 3.8 이상 표준 라이브러리만 쓴다.
- 줄표 설명 · 화살표 · 콜론 설명 · 대구 · 상투어 · 분열문 · 변환 공식 · 번역투 · 이모지 · 긴 문장 · 굵은 글씨 과다를 줄 단위로 보여 준다.
- 한 번은 괜찮고 몰리면 티가 나는 것은 문서 전체에서 센다. 기준을 넘으면 `[문서]` 줄로 위치와 함께 보여 준다.
  연결어미 뒤 쉼표 6회, "~를 통해" 3회, "~에 대해" 3회, "~할 수 있다" 4회, "~되고 있다" 3회.
  기준은 humanize-korean 규칙집의 값을 따랐다.
- 걸린 줄이 있으면 종료 코드 1, 없으면 0 이다.
- 긴 문장을 잴 때 URL 은 뺀다. 출처 목록이 통째로 걸리던 것을 막는다. 별점(★☆)은 척도라 이모지로 보지 않는다.
- 걸린 것이 다 틀린 것은 아니다. 사람이 판단할 것은 이렇다.
  - 날짜 범위(`09.21~09.23`)나 숫자 범위
  - 양식이 정한 `항목 : 설명` 형식 (규칙 2)
  - 목차 줄, 표 셀 안의 목록
- 괄호 덧붙임은 검사하지 않는다. 양식의 `o 항목 (설명)` 과 출처 표기(`(일반적으로 알려진 바)`)까지 걸려
  실제 문서에서 잡음이 더 많았다. 쓰는 순서 6 에서 눈으로 본다.
- 결과가 0 이어도 끝이 아니다. 산출물 위주인지는 사람이 본다(규칙 1).
