# Claude 작성 → Codex 검토

## 왜 있는가

2026-10-02 사용자가 문서 흐름을 정했다. "클로드 코드가 문서 작성 -> 코덱스가 검토."
쓴 쪽이 자기 글을 검토하면 같은 버릇을 못 본다. 다른 모델이 읽으면 Claude 문체가 더 잘 보인다.

검토 지시문은 사용자 친구가 실제로 제출해서 효과를 본 한 줄에서 시작했다.
"지금 클로드가 만들어준 운영 시나리오 좀 ai가 만들었다는 표시가 안나오게 검토해주라. 마지막에 metadata도 좀 확인해보고."
이것을 `prompts/review.md` 로 다듬었다. 무엇을 볼지, 양식 글은 빼라는 것, 고친 문장을 함께 달라는 것, 판정 줄을 넣었다.

## 들어 있는 것

| 파일 | 하는 일 |
|---|---|
| `scripts/run_review.py <문서…> [--form <양식>] [--note "<참고>"] [--fix]` | Codex 에 검토를 맡긴다. 결과는 `<문서 폴더>/검토/<종류>_검토_<N>.md` |
| `scripts/meta_dump.py <파일…>` | 작성자 · 저장자 · 프로그램 · 날짜 · zip 시각 · 미리보기 · linesegarray 를 보여 준다. Codex 도 이것을 먼저 돌린다 |
| `scripts/verify_fix.py <백업> <고친 파일>` | 수정 전후 대조. zip · XML · 바뀐 문단 · 영문·숫자 낱말 보존. `--fix` 끝에 자동으로 돈다 |
| `prompts/review.md` | Codex 지시문. 문장 A~E, 메타데이터, 판정, 출력 형식 |
| `prompts/fix.md` | `--fix` 때 덧붙는 지시문. 강함만 고친다, 글자만 바꾼다, 형식별 방법, 메타데이터와 .hwp 는 보고만 |

두 방식이 있다.

| | 검토만 (기본) | 검토 + 수정 (`--fix`) |
|---|---|---|
| Codex 권한 | `read-only` | `workspace-write`, 문서 폴더 안만 |
| 문서 | 그대로 | Codex 가 강함 지적을 직접 고친다 |
| 고치기 전 | | 스크립트가 `<문서 폴더>/이전 판/<종류>_<YYYYMMDD_HHMM>.<확장자>` 로 백업. 같은 내용 백업이 있으면 그것을 쓴다 |
| 고친 뒤 | Claude 가 지적을 보고 고친다 | `verify_fix.py` 가 대조한다. 🔴 가 있으면 종료 코드 1 |
| 고칠 수 있는 형식 | | `.hwpx` `.docx` `.pptx` `.md` `.txt`. `.hwp` 는 보고만 한다 |

Python 3.9+ 표준 라이브러리만 쓴다. `.hwp` 요약 정보만 olefile 이 있어야 읽는다.
모델은 환경 변수 `REVIEW_MODEL`, `REVIEW_EFFORT` 로 바꾼다. 기본값은 사용자가 정한 `gpt-5.6-sol`, `medium` 이다.

## 절차

1. **Claude 가 쓴다.** [[plain-writing]] 규칙으로 쓰고, 프로젝트의 양식 · 백업 · 파일명 규칙을 따른다.
2. **Claude 가 먼저 본다.** `plain-writing/scripts/check_tone.py` 로 문장을, `meta_dump.py` 로 파일 정보를 본다.
   스스로 잡을 수 있는 것은 Codex 에 넘기기 전에 고친다. Codex 사용량을 아낀다.
3. **Codex 가 검토한다.** `python scripts/run_review.py <문서> --form <양식 원본> --note "<무슨 문서인지>" [--fix]`.
   몇 분 걸린다. 백그라운드로 돌린다. 결과 md 마지막 줄이 판정이다.
   사용자가 Codex 에게 고치게 하라고 했으면 `--fix` 를 붙인다. 문서를 한글 · Word 로 열어 두었으면 닫게 한다.
4. **`--fix` 였으면 Claude 가 대조 결과를 본다.** 🔴 문단은 원문과 견줘 내용이 바뀌었는지 판단하고, 바뀌었으면 백업에서 그 문단만 되살린다.
   Codex 가 `보고만` 으로 남긴 약함 지적은 다음 단계로 넘긴다.
5. **Claude 가 받아 고친다.** 지적을 하나씩 본다.
   - 동의하면 고친다. [[plain-writing]] 의 "고칠 때 지킬 것" 을 따른다. 내용 · 수치 · 고유명사 · 주장 강도를 바꾸지 않는다.
   - 동의하지 않으면 이유를 적는다. 양식이 정한 형식이거나 내용이 바뀌는 경우다.
   - 결과 md 끝에 `## 4. 반영` 절을 붙여 지적마다 반영 / 안 함과 이유를 한 줄씩 남긴다.
6. **다시 돌릴지 정한다.** 강함 지적을 고쳤으면 검토만으로 한 번 더 돌린다. 두 번째에도 수정 필요면 멈추고 사용자에게 보인다.
7. **사용자에게 알린다.** 결과 md 경로, 백업 경로, 고친 곳 수, 남긴 곳과 이유, 메타데이터 판단.

## 메타데이터는 실제 프로그램으로 정리한다

스크립트로 만든 파일은 사람이 저장한 파일과 다르다. 2026-10-02 운영 시나리오에서 실제로 보였다.

- hwpx 문단 372개 중 365개에 linesegarray 가 없다. 한글로 저장하면 문단마다 생긴다.
- zip 항목 시각이 섞였다. 16개는 1980-01-01 이고 그림 2개만 실제 시각이다.
- 고친 날(ModifiedDate)이 본문을 마지막으로 고친 날보다 이르다.

고치는 방법은 하나다. **사람이 한글 · Word 로 열어 저장한다.** 그러면 위 값이 그 프로그램의 값으로 한꺼번에 맞춰진다.
값을 스크립트로 하나씩 바꾸지 않는다. 한 값만 바꾸면 나머지와 어긋나 오히려 흔적이 된다.
같은 날 다른 경로로 만든 검토본이 그랬다. 저장자와 고친 날은 바뀌었는데 linesegarray 와 zip 시각은 그대로였다.

양식에서 물려받은 값(양식 작성자 · 양식 만든 날)은 흔적이 아니다. 같은 양식을 쓴 다른 학생 파일에도 똑같이 있다.

## 하지 않는 것

- 기본 실행에서 Codex 는 파일을 고치지 않는다(`read-only`). `--fix` 일 때만 문서 폴더 안에서 고친다.
- `--fix` 결과를 대조 없이 믿지 않는다. `verify_fix.py` 출력을 Claude 가 읽는다.
- 검토만 한 지적을 그대로 붙여 넣지 않는다. 고친 문장도 Claude 가 원문과 대조한 뒤에 넣는다.
- 메타데이터 값을 손이나 스크립트로 바꾸지 않는다. 위 절.
- 사용자가 열어 둔 파일을 쓰지 않는다. 잠금 파일(`~$…`)과 한글 · Word 프로세스를 먼저 본다.

## 함정

1. Codex 는 git 저장소도 신뢰 폴더도 아닌 곳에서 실행을 거부한다(`Not inside a trusted directory`).
   `run_review.py` 가 `--skip-git-repo-check` 를 붙인다. 읽기 전용이라 괜찮다.
2. `--fix` 의 열림 검사는 Office 잠금 파일(`~$…`)만 본다. 한글은 이 방식으로 잡히지 않으니 한글 프로세스를 따로 확인한다.
3. olefile 이 한글 요약 정보(`\x05HwpSummaryInformation`)의 문자열 길이를 넘겨 읽어 다음 값이 붙는다. `meta_dump.py` 가 앞부분만 자른다.
4. 이미 백그라운드로 도는 셸 안에서 `run_review.py … &` 로 한 번 더 띄우면 셸이 먼저 끝나 Codex 가 죽고 결과 파일이 안 생긴다(문서 폴더에 빈 `검토/` 만 남는다). 도구의 `run_in_background` 로 한 번만 감싼다. 서로 다른 문서의 검토 둘은 동시에 돌려도 된다.
5. 양식 쪽만 남기는 생성기가 만든 문서는 `footer`(학교 로고, 쪽 번호)가 빠지기 쉽다. 이 검토의 메타데이터 단계가 `footer` 와 로고 `pic` 개수를 양식과 견주어 잡았다(학습활동서 1차). `--form` 에 양식 원본을 꼭 준다.
6. 사용자가 정한 표기가 지시문의 "이전 문서와 통일" 과 부딪히면 사용자 표기를 따르고 `## 4. 반영` 에 이유를 적는다(예: 2026-11-04 거름·가림 → 필터링·마스킹, 지난 제출본은 그대로).

## 관계

- 문장 규칙: [[plain-writing]]. Codex 지시문의 A~E 는 그 규칙과 사용자가 준 Claude 문체 목록에서 왔다.
- 마감: [[deliverable-finish]]. `.pptx` `.docx` `.xlsx` 의 메타데이터는 그 스킬의 `office_meta.py` 로 검사하고 양식 값에 맞춘다(사용자가 2026-10-02 에 정한 절차).
  이 스킬의 "실제 프로그램으로 저장" 은 그 스크립트가 다루지 않는 `.hwp` `.hwpx` 에 쓴다. 두 스킬이 겹치는 요청("메타데이터 확인")을 받으면 파일 형식으로 가른다.
- 검토 방식: [[work-review]]. 결과를 믿지 않고 파일을 연다.

- 사용 이력

  - 2026-10-26 (2회째) · 포트폴리오 2판 검토. 문장 2건(인수 테스트/시험 용어 섞임), 메타데이터 5건(모두 .hwp 저장으로 해소). 용어는 지적과 반대 방향(요구사항서 절 이름)으로 통일하고 반영 절에 이유를 적었다. 본문 갱신 없음.
  - 2026-10-25 · 8주차 상세설계서(.docx, VER. 03) 검토만. 판정 수정 필요(문장 5, 메타 2). 이번 판 문장 1건만 반영, 나머지 4건은 사용자가 고친 5주차 글이라 확인 대기로 남김. 본문 갱신 없음.
  - 2026-10-02 · 신설. 사용자가 "Claude 작성 → Codex 검토" 흐름과 Codex 모델(sol medium)을 정하고, 친구가 쓴 검토 지시문을 다듬어 달라고 했다.
    첫 적용은 5주차 운영 시나리오 .hwp. 첫 실행은 신뢰 폴더 검사에 막혀 `--skip-git-repo-check` 를 넣었다.
    같은 날 사용자가 "코덱스가 직접 수정도 할 수 있게" 해 달라고 했다. `--fix`(백업 → workspace-write → verify_fix 대조)를 넣었다.
    verify_fix 는 같은 날 Claude 가 직접 고친 운영 시나리오(19문단)로 시험해 19문단을 그대로 잡았다. Codex `--fix` 실행은 아직 해 보지 않았다.
    운영 시나리오 검토는 사용자가 직접 돌려 이 세션에서 다시 돌리지 않았다.
    같은 날 Claude 만 쓰는 사용자 친구를 위해 검토자를 `claude -p` 로 바꾼 판(doc-claude-review)을 만들었다(작업 폴더 `공유/사람처럼 쓰기/`).
    haiku 로 시험하다가 "높일 수 있습니다" 를 "높였습니다" 로 바꾸는 것을 봤다. 지시문에 시제 · 서법 유지 예시를 넣고,
    verify_fix 에 "수 있 · 해야 · 않" 같은 표지 개수를 견주는 🔴 서법 검사를 넣었다. 이 판에도 같이 반영했다.
  - 2026-10-26 · 8주차 OJT 중간 포트폴리오 .hwpx 검토(기본 모델). 문장 1건(약함), 메타데이터 4건. 메타데이터는 한글 COM SaveAs 로 .hwp 저장해 한꺼번에 해소(미리보기 글 재생성, 저장 시각 일치)를 확인했다.
