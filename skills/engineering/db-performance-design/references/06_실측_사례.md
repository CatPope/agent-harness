# 실측 사례 — 첫 적용 (2026-09-30)

다음 검토에서 "이 규모면 무엇이 느려지나" 를 가늠하는 기준이다. 수치는 그 기계·그 데이터의 값이다. 그대로 옮겨 쓰지 않고 다시 잰다.

## 대상과 환경

- 1인 프로젝트. PC 마다 로컬 대화 DB(메신저 본문 + FTS5), 서버에 메타 DB(채팅방·링크·태그·기기·전달 큐). 둘 다 SQLite.
- 윈도 11 개발 PC, 파이썬 3.14, SQLite 3.50.4. 서버 VM 은 아직 없었다.
- 합성 데이터. 실제 DB 에서는 분포만 집계했다(본문 평균 44 B, 100 B 미만 92%, 채팅방 25개 중 상위 1개가 29%, 발화자 20명 중 상위 1명이 45%).
  실제 증가 속도는 월 600건이었다.

## 로컬 DB

| 규모(5년) | 현 설계 크기 | 개정안 크기 | 적재 (현 / 개정) |
|---|---|---|---|
| 3.6만 (지금 속도) | 12.0 MB | 9.9 MB | 52 s / 6.4 s |
| 18만 (5배) | 53.8 MB | 43.4 MB | 134 s / 24.5 s |
| 180만 (50배) | 524 MB | 419 MB | 334 s / 185 s |

적재는 대화 파일(채팅방 × 날짜) 하나에 커밋 하나였다. 현 설계는 DELETE + FULL, 개정은 WAL + NORMAL 이다.

| 질의 (ms) | 3.6만 현 / 개정 | 180만 현 / 개정 | 느려진 이유 |
|---|---|---|---|
| 큰 프로젝트 타임라인 | 23 / 0.03 | 443 / 0.03 | 프로젝트의 행을 전부 모아 정렬 |
| 인물 타임라인 | 9.8 / 0.03 | 366 / 0.03 | 그 사람의 행을 전부 모아 정렬 |
| 채팅방 통계 | 40 / 1.5 | 639 / 106 | 표를 훑음(덮는 색인이면 색인만 훑음) |
| 참여자 계산 | 44 / 1.5 | 1,043 / 72 | 표를 훑고 GROUP BY 정렬 |
| 관련도순 검색 20건 | 1.7 / 8.0 | 115 / 474 | bm25 가 맞는 행 전부를 채점. 개정안은 재현율이 높아 맞는 행이 많다 |
| 최신순 검색 20건 | 0.09 / 0.13 | 0.24 / 0.11 | 일찍 멈춘다 |

개정안 값은 질의 모양을 고친 뒤의 값이다. 고치기 전에는 전체 타임라인 549 ms, 큰 채팅방 173 ms 였다(`02` §4).

## 동시 부하 (서버, 링크 1.5만)

폴러 하나가 0.3초마다 기기 확인 → `last_seen_at` 쓰기 → 대기 작업 → 바뀐 태그를 한다. 30초 주기 장치 100대쯤이다.

## 이 사례에서 얻은 기준

- 행이 수만 건이면 설계가 서툴러도 대개 50 ms 안이다. 문제는 수십만 건부터 "맞는 행 전부 정렬" 모양에서 드러난다.
- 크기보다 먼저 볼 것은 검색 재현율, 잠금 설정, 시각 형식, 멱등 키였다.
- 반정규화 후보는 먼저 색인·질의 모양으로 재 본다. 이 사례에서는 셋 중 하나만 구조를 바꿨고 그것도 중복이 아니라 슈퍼타입 조정이었다.
