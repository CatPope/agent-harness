# 하드웨어에서 B-tree 까지

DB 설계 규칙은 저장장치가 어떻게 움직이는지에서 나온다. 이 문서는 그 사슬을 아래에서 위로 적는다.
수치는 출처를 붙였다. 출처 없는 것은 "일반적으로 알려진 바" 라고 적었다.

## 1. 계층마다 지연이 다르다

| 동작 | 지연 | 비고 |
|---|---|---|
| L1 캐시 참조 | 0.5 ns | |
| 주기억장치 참조 | 100 ns | |
| SSD 에서 4 KB 임의 읽기 | 150 µs | 메모리의 약 1,500배 |
| SSD 에서 1 MB 순차 읽기 | 1 ms | |
| 하드디스크 탐색 | 10 ms | |

출처: Jeff Dean·Peter Norvig 의 지연 표(https://gist.github.com/jboner/2841832, 2026-09-30 열람). 대략값이다. 장비마다 다르다.

**그래서** DB 의 속도는 대부분 두 가지로 정해진다.

1. 캐시에 없는 페이지를 **몇 번** 읽는가
2. 커밋마다 저장장치가 "다 썼다" 고 답할 때(fsync)까지 **몇 번** 기다리는가

CPU 가 SQL 을 해석하는 시간은 보통 이 둘보다 작다.

## 2. DB 는 파일을 페이지 단위로 읽고 쓴다

- SQLite 는 파일을 같은 크기의 페이지로 나눈다. 512~65536 B, 기본 4096 B(https://www.sqlite.org/fileformat2.html).
- PostgreSQL 도 표와 색인을 고정 크기 페이지 배열로 둔다. 보통 8 kB(https://www.postgresql.org/docs/current/storage-page-layout.html).
- 행 하나를 읽어도 그 행이 든 **페이지 하나**를 읽는다.

**그래서** 행이 작을수록 한 페이지에 많이 들어가고, 같은 질의가 읽는 페이지 수가 준다.
행을 작게 만드는 규칙(해시는 BLOB, 시각은 INTEGER)은 여기서 나온다.

## 3. 캐시

- SQLite 는 연결마다 페이지 캐시를 둔다. 기본 `cache_size=-2000` 으로 약 2 MB(https://www.sqlite.org/pragma.html).
- 그 아래에 운영체제의 파일 캐시가 있다. 자주 읽는 페이지는 대개 메모리에 있다.
- 자주 쓰는 데이터가 메모리에 다 들어가면 디스크를 거의 읽지 않는다. 넘치면 임의 읽기마다 SSD 지연이 붙는다.

**그래서** 용량 산정은 "파일이 몇 GB 인가" 보다 "자주 읽는 부분이 메모리에 들어가는가" 가 중요하다.
작은 VM 이면 이 점을 먼저 본다.

## 4. B-tree

표와 색인은 페이지로 된 균형 트리다. 뿌리에서 잎까지 거리가 어디서나 같다.

| | SQLite 표 B-tree | SQLite 색인 B-tree |
|---|---|---|
| 키 | 64비트 정수 rowid | 색인 열 값 + rowid |
| 자료 | **잎에만** (B+tree) | 키만. **내부 페이지 칸도 항목**이다 |
| 페이지 머리 | 잎 8 B, 내부 12 B | 같음 |

출처: https://www.sqlite.org/fileformat2.html

- 깊이는 항목 수의 로그로 늘어난다. 수백만 행 색인도 깊이가 4~5 이고 6 은 거의 없다
  (Markus Winand, https://use-the-index-luke.com/sql/anatomy/the-tree).
- 위쪽 몇 층은 늘 캐시에 있다. 그래서 한 번 찾는 데 실제로 디스크를 읽는 것은 잎 근처 한두 페이지다.

**실측 예**: 1,386행 표와 그 색인들은 모두 깊이 2 였다. 4 KB 페이지 하나에 색인 항목이 70~350개 들어갔다.

## 5. 색인으로 찾는 비용

SQLite 질의 계획 문서(https://www.sqlite.org/queryplanner.html)의 모형이다.

| 찾기 | 비용 |
|---|---|
| 전체 훑기 | N 에 비례 |
| rowid 로 한 행 | log N |
| 색인으로 한 행 | 색인 탐색 + 표 탐색 = 2 × log N |
| 색인으로 K 행 | (K + 1) × log N. 다음 항목은 대개 같은 페이지라 싸다 |
| 덮는 색인(covering) | 표를 안 간다. **약 2배 빠르다** |

느린 색인 찾기에는 원인이 둘 있다(use-the-index-luke, slow-indexes).

1. **잎 사슬을 오래 따라간다.** 조건에 맞는 항목이 많으면 잎을 여러 장 넘긴다.
2. **표를 찾아간다.** 맞는 행이 표 여기저기에 흩어져 있으면 행마다 다른 페이지를 읽는다.

## 6. 정렬과 LIMIT

- `ORDER BY` 를 색인이 받으면(색인 순서 = 요청한 순서) 앞에서부터 읽다가 LIMIT 에서 멈춘다. 비용은 n 에 비례한다.
- 못 받으면 맞는 행 **전부**를 모아 정렬한다. 질의 계획에 `USE TEMP B-TREE FOR ORDER BY` 가 뜬다(https://www.sqlite.org/eqp.html).
  비용은 LIMIT 이 아니라 **맞는 행 수**에 비례한다.

**이것이 "데이터가 늘면 느려진다" 의 가장 흔한 모양이다.** 1년치에서 1 ms 인 질의가 5년치에서 수백 ms 가 된다.
복합 색인의 열 순서(등호 → 범위 → 정렬)는 이 문제를 막으려는 것이다.

## 7. 조인

- SQLite 는 바깥 표의 행마다 안쪽 표를 찾는 중첩 반복(nested loop) 방식이다.
- 안쪽 조인 열에 색인이 있으면 행마다 log N 이다. 없으면 바깥 행 수 × 안쪽 행 수가 된다.
- 조인이 많다고 느린 것이 아니다. **색인 없는 조인 열**이 느리다.

## 8. 쓰기 경로

행 하나를 바꿔도 여러 페이지를 쓴다.

- 그 행이 든 표 페이지 하나
- 색인마다 페이지 하나씩. 색인 수가 곧 쓰기 증폭이다
- 커밋할 때 내구성을 위해 fsync(윈도는 FlushFileBuffers)를 기다린다

| 저널 모드 | 커밋마다 기다리는 것 |
|---|---|
| DELETE(롤백 저널, SQLite 기본) | 저널 쓰기와 동기화, DB 쓰기와 동기화, 저널 지우기 |
| WAL + FULL | WAL 끝에 붙이고 한 번 동기화 |
| WAL + NORMAL | 커밋 때는 동기화하지 않는다. 체크포인트 때만 한다 |

출처: https://www.sqlite.org/wal.html , https://www.sqlite.org/atomiccommit.html

**실측**(윈도 11 개발 PC, SQLite 3.50.4, `scripts/commit_bench.py`, 2026-09-30)

| 모드 | 커밋 p50 | 초당 커밋 |
|---|---|---|
| DELETE + FULL | 2.18 ms | 430 |
| WAL + FULL | 1.22 ms | 370 |
| WAL + NORMAL | 0.015 ms | 57,100 |

fsync 비용은 저장장치와 가상화에 따라 몇 배씩 다르다. **운영할 기계에서 다시 잰다.**

작은 트랜잭션을 많이 하면 커밋 비용이 전부다. 같은 7,200건을 대화 파일 3,413개로 나눠 커밋했더니
DELETE+FULL 은 10.1초, WAL+NORMAL 은 0.97초 걸렸다.

## 9. 동시성

- SQLite 에서 쓰는 쪽은 **언제나 하나**다(WAL 도 같다).
- 롤백 저널은 커밋하는 동안 읽기도 막는다. 한 쓰기가 계속 커밋하는 3초 동안, 기다리지 않는 읽기 306번 중 261번이 막혔다.
- WAL 에서는 읽기와 쓰기가 서로 막지 않는다. 같은 시험에서 막힌 읽기는 1~2번이었다.

## 10. 흔한 착각

| 착각 | 실제 |
|---|---|
| 정규화하면 조인 때문에 느리다 | 조인 열에 색인이 있으면 행마다 log N 이다. 느린 것은 대개 정렬·거르기를 색인이 못 받는 질의다 |
| 질의를 여러 번 나누면 느리다(N+1) | 클라이언트/서버 DB 에서는 왕복 비용 때문에 맞다. SQLite 는 같은 프로세스라 웹 페이지 하나에 200문장도 괜찮다(https://www.sqlite.org/np1queryprob.html) |
| 행이 많아지면 SQLite 가 못 버틴다 | DB 최대 281 TB. 하루 10만 요청 미만 사이트는 문제없다(보수적 추정, https://www.sqlite.org/whentouse.html). 쓰기가 폭주하거나 서버가 여러 대일 때 클라이언트/서버 DB 를 본다 |
| 색인은 많을수록 좋다 | 색인마다 쓰기 비용과 공간이 든다. 받는 질의가 없는 색인은 두지 않는다 |
