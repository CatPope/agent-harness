# 성능 데이터 모델링 — 국내 표준 절차와 반정규화

국내 SI·DA 실무가 쓰는 절차다. 한국데이터산업진흥원 「SQL 전문가 가이드」 1과목 2장(데이터 모델과 성능)에 있다.
원서는 열어 보지 못했다. 그 장을 옮긴 학습 정리 두 편으로 확인했다(2026-09-30 열람).

## 1. 여섯 단계

| 순서 | 할 일 | 이 스킬의 절차 |
|---|---|---|
| ① | 정규화를 정확히 한다 | 1 |
| ② | DB 용량을 산정한다 | 2 |
| ③ | DB 에 일어나는 트랜잭션 유형을 파악한다 | 3 |
| ④ | 용량과 트랜잭션 유형에 따라 반정규화한다 | 5 |
| ⑤ | 이력 모델, PK/FK, 슈퍼타입/서브타입을 조정한다 | 4·5 |
| ⑥ | 성능 관점에서 데이터 모델을 검증한다 | 7 |

실무에서는 정규화를 끝내 놓고, **용량이 몰려 늘어나는 엔터티**를 찾아 그 트랜잭션을 본다.
CRUD 표와 시퀀스 다이어그램에서 SQL 의 조인 관계와 쓰는 열을 뽑은 뒤 반정규화를 한다.
PK 는 성능에 좋은 순서로 열을 둔다.

**정규화가 조회를 느리게만 하는 것은 아니다.** 열이 많은 표에서 자주 쓰는 몇 열을 떼어 내면 읽는 페이지가 준다.
같은 형식의 속성이 여러 열에 있으면(전화1, 전화2 …) 열마다 색인을 두는 대신 행으로 정규화하는 편이 낫다.

## 2. 반정규화 절차

반정규화는 성능·개발·운영의 편의를 위해 **중복을 각오하고** 표를 합치거나 나누거나 더하는 것이다.

1. **대상을 조사한다.**
   - 자주 쓰는 범위 조회가 있는가
   - 대량 데이터를 범위로 읽는가
   - 통계성 처리(집계)가 잦은가
   - 조인이 지나치게 많은가
2. **다른 방법을 먼저 검토한다.** 뷰, 클러스터링·색인 조정, 파티셔닝, 응용 로직 변경.
   이 단계를 건너뛰면 반정규화가 기본값이 된다. 가장 자주 빠뜨리는 단계다.
3. **적용한다.**

## 3. 반정규화 기법

| 구분 | 기법 | 내용 |
|---|---|---|
| 표 병합 | 1:1 · 1:M · 슈퍼/서브타입 병합 | 늘 함께 읽는 표를 합친다 |
| 표 분할 | 수직 분할 | 열 단위로 1:1 로 나눈다. 늘 쓰는 열과 가끔 쓰는 큰 열을 나눌 때 |
| | 수평 분할 | 행 단위(기간·지역)로 나눈다. 파티셔닝(범위·목록·해시) |
| 표 추가 | 중복 표 | 다른 곳(원격)에 같은 표를 둔다 |
| | 통계 표 | 집계를 미리 계산해 둔다 |
| | 이력 표 | 마스터의 레코드를 이력에 중복해 둔다 |
| | 부분 표 | 자주 쓰는 열만 모은 표 |
| 열 | 중복 열 | 조인을 줄이려고 다른 표의 열을 복사한다 |
| | 파생 열 | 계산값을 미리 저장한다 |
| | 이력 표의 열 추가 | 최신 여부, 시작·끝 일자 |
| | PK 에 의한 열 추가 | 복합 PK 의 일부를 따로 조회할 때 |
| | 오작동 대비 열 | 이전 값을 보관한다 |
| 관계 | 중복 관계 | 조인 경로를 줄이려고 관계를 하나 더 둔다 |

슈퍼타입/서브타입을 표로 바꾸는 방법은 셋이다. **트랜잭션이 어떻게 읽는가로 고른다.**

| 방법 | 고르는 경우 |
|---|---|
| 개별 표(서브타입마다 표) | 서브타입마다 따로 처리한다 |
| 슈퍼 + 서브 분리 | 공통 부분을 함께, 개별 부분을 따로 처리한다 |
| 하나로 통합 | 전체를 늘 함께 조회한다 |

## 4. 적용 판단표 (이 스킬의 기준)

반정규화는 아래를 **모두** 만족할 때만 한다.

| 조건 | 확인하는 법 |
|---|---|
| 그 질의가 목표 시간을 넘는다(또는 넘을 규모가 온다) | 합성 데이터 실측. 추측하지 않는다 |
| 색인·질의 재작성으로 목표를 못 맞춘다 | `explain_check.py` 로 두 안을 모두 잰다 |
| 중복을 맞추는 경로를 하나로 정할 수 있다 | 아래 5절 |
| 맞추는 비용(쓰기 증폭, 갱신 범위)이 읽기에서 얻는 것보다 작다 | 갱신 빈도 × 갱신 행 수를 적는다 |

## 5. 중복을 누가 맞추는가

| 방법 | 맞는 경우 | 주의 |
|---|---|---|
| 트리거 | 쓰기 경로가 여럿이다. DB 가 보장해야 한다 | 트리거는 쓰기마다 돈다. 대량 적재가 느려진다 |
| 쓰기 코드 한 곳 | 쓰는 프로그램이 하나다(적재기 같은) | 다른 경로(수작업 SQL, 새 도구)가 생기면 깨진다. 그 사실을 스키마 주석에 적는다 |
| 배치 재계산 | 조금 늦어도 된다(통계·목록 정렬값) | 늦는 정도를 화면에 드러낸다 |
| 읽을 때 계산(반정규화 안 함) | 계산이 색인으로 싸다 | 기본값. 실측이 느리다고 말할 때만 바꾼다 |

## 6. 멱등 키가 정당한 중복을 합치지 않게

재적재해도 같은 행이 두 번 들어가지 않게 해시 키를 쓴다. 해시 입력이 행을 다 구별하지 못하면 다른 행이 하나로 합쳐진다.
메신저 로그는 시각이 분 단위라 같은 분에 같은 사람이 같은 말("네")을 두 번 하면 한 건만 남는다.

같은 파일 안에서 같은 입력이 n번째로 또 나오면(n ≥ 1) 해시 입력 끝에 `|n` 을 붙인다.
첫 번째는 옛 값 그대로라 기존 행과 맞고, 같은 파일을 다시 읽어도 같은 키가 나온다.

## 7. 사례 — 반정규화 후보 셋을 잰 결과

1인 프로젝트, SQLite 두 개(로컬 대화 DB, 서버 메타 DB). 합성 데이터 5년치(`06_실측_사례.md`).

| 후보 | 기법 | 조사한 질의 (180만 건) | 다른 방법 | 결과 |
|---|---|---|---|---|
| 대화 표에 프로젝트 번호 복사 | 중복 열 | 프로젝트 타임라인 443 ms | 질의 모양 (`02` §4) | 0.03 ms. 기각 |
| 채팅방·발화자 통계 표 | 통계 표 | 참여자 계산 1,043 ms | 덮는 색인 `(source_id, person_id)` | 72 ms, 실제 규모(3.6만)에서 1.5 ms. 조건부 |
| 서버 자료 목록(채팅방 ∪ 링크) | 슈퍼타입 조정 | 목록 첫 페이지 87 ms (링크 60만) | 색인으로는 UNION 정렬을 못 없앤다 | 슈퍼타입 한 표 + (최근 활동, id) 색인으로 0.026 ms. 채택 |

셋째는 같은 값을 두 곳에 두지 않는다. 공통 부분(종류, 프로젝트, 이름, 최근 활동)을 슈퍼타입 표로 올리고
개별 부분을 상세 표 둘에 둔다. 태그 표도 둘에서 하나가 되어 API 와 동기화 질의가 준다.
대가는 목록 색인 셋만큼의 크기와 쓰기다(링크 60만에서 124 MB 가 147 MB, 적재 9초가 31초).

통계 표를 켠다면 대화가 들어오고 지워질 때 트리거가 맞춘다. 지울 때 "마지막 시각" 은 줄일 수 없어 다시 계산해야 한다.
이 비용을 적어 두고, 켜는 조건(건수·동기화 주기)을 숫자로 정해 둔다.

## 8. 흔한 실수

- 규모를 재지 않고 "성능을 위해" 미리 반정규화한다. 맞출 경로가 늘어 버그가 는다.
- 목록을 JSON 열 하나에 넣는다. 거르기·색인이 안 되고 부분 갱신이 경합을 부른다. 화면 표시용 파생값일 때만 쓴다.
- 캐시 열을 두고 갱신 경로를 정하지 않는다. 한 번 어긋나면 어느 쪽이 맞는지 모른다.
- 파생 표가 원천보다 먼저 갱신되거나 늦게 갱신되는 순서를 정하지 않는다. 같은 트랜잭션에서 둘을 바꾼다.
