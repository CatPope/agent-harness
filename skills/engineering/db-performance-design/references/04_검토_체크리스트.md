# ERD·스키마 검토 체크리스트

검토 보고서의 뼈대로 쓴다. 항목마다 "지금 값 / 문제 / 권고 / 근거(실측·문서)" 를 적는다.

## 전제

- [ ] 엔진과 판, 운영 기계(OS·저장장치·가상화), 같은 파일을 쓰는 프로세스 수
- [ ] 쓰는 쪽은 몇인가. 읽기와 쓰기가 동시에 있는가
- [ ] DB 가 유일본인가(원본이 사라지는 데이터가 있는가). 유일본이면 유실 위험이 성능보다 앞선다

## 표마다

- [ ] PK 종류: 정수 rowid / WITHOUT ROWID / 무작위 키. 무작위 키면 이유
- [ ] 행 크기(실측 바이트, 색인 포함). 큰 열(본문·BLOB)은 어디에 있나
- [ ] 증가 등급: 고정 / 느림 / 빠름 / **끝없음**. 끝없으면 지우는 규칙과 그 규칙이 쓸 색인
- [ ] 시각 열의 형식과 시간대가 표끼리 같은가
- [ ] 해시·토큰을 글자(hex)로 두지 않았나
- [ ] 논리 삭제(`deleted=1`) 행을 언제 물리 삭제하나
- [ ] 멱등 키가 정당한 중복까지 합치지 않는가(같은 분·같은 사람·같은 말)

## 색인마다

- [ ] 이 색인을 쓰는 질의 이름
- [ ] 다른 색인(UNIQUE 포함)의 앞부분과 겹치지 않는가
- [ ] 복합 색인 열 순서가 등호 → 범위 → 정렬인가
- [ ] FK 자식 열이 어떤 색인의 앞 열인가

## 질의마다 (트랜잭션 유형 목록에서)

- [ ] 빈도, 읽는 행 수, 목표 시간
- [ ] 질의 계획: `SEARCH`/`SCAN`, `USE TEMP B-TREE` 가 있는가
- [ ] `ORDER BY … LIMIT` 이 색인으로 일찍 멈추는가
- [ ] 페이지 나누기가 OFFSET 인가 커서(keyset)인가. 뒤쪽 페이지 비용, 새 행이 들어올 때 중복·누락
- [ ] 합계(`count`)를 요청마다 계산하는가. 비용은
- [ ] 합성 데이터로 1·3·5년, 지금·5배·50배에서 잰 시간
- [ ] 색인·통계를 바꾼 **뒤에** 핵심 질의의 계획을 다시 봤는가(조인 순서가 뒤집혀 전부 정렬하는 일)
- [ ] 두 표를 UNION 해 정렬하는 목록이 있는가. 있으면 슈퍼타입으로 합칠지
- [ ] 동시 부하에서 p99·최대 지연(오류 수만 보지 않는다)

## 검색

- [ ] 텍스트 언어와 토크나이저가 맞는가(한국어면 [[korean-fulltext-search]])
- [ ] 사용자 입력을 이스케이프하는가
- [ ] 결과 정렬(관련도 vs 최신순)과 그 비용
- [ ] 색인 동기화를 **실제로** 검사하는가(`count(*)` 비교는 외부 콘텐츠 표에서 늘 같다)

## 운영

- [ ] 저널 모드·동기화 수준·busy_timeout
- [ ] 쓰기 트랜잭션을 `BEGIN IMMEDIATE` 로 여는가
- [ ] 드라이버의 트랜잭션 기본 동작(파이썬 `sqlite3` 의 암묵적 BEGIN)
- [ ] 통계(`PRAGMA optimize`) 주기
- [ ] FTS `merge`/`optimize` 주기
- [ ] 백업 방법(백업 API·`VACUUM INTO`)과 세대 보관, 복원 시험
- [ ] 무결성 검사(`quick_check`, FTS `integrity-check`)
- [ ] 크기 추이를 보는 방법(`sqlite_pages.py`)
- [ ] "정상" 이라고 보고하는 점검이 실제로 이상을 잡는가(거짓 정상 금지)
