# DB 성능 설계

## 왜 있는가

2026-09-30, 1인 프로젝트(SQLite 두 개)의 ERD 를 본 사용자가 물었다.
"DB 동작 방식을 하드웨어 수준부터 이해하고 짠 게 맞나요? 정규화는 잘 됐는데 성능이 걱정됩니다."
예전 상사도 앞선 판을 보고 "이런 식이면 1년 안에 DB 가 터지고 검색이 안 된다" 고 했다.

답은 "아니다" 였다. ERD 는 정규화와 참조 무결성만 따졌다. 용량, 질의 유형, 색인, 저널 설정, 실측이 없었다.
재 보니 그 규모에서 속도는 문제가 아니었다. 문제는 다른 곳에 있었다.
한국어 검색이 조사 붙은 낱말을 못 찾았다. 검색어의 점·하이픈·콜론이 문법 오류를 냈다.
롤백 저널이 쓰는 동안 읽기를 막았다. "색인 동기화됨" 검사는 늘 참이었다.

**논리 설계가 끝났다고 설계가 끝난 것이 아니다.** 이 스킬은 그 검토에서 나온 절차와 규칙이다.

## 절차

0. **전제를 적는다.** 엔진과 판, 같은 파일을 쓰는 프로세스 수, 쓰는 쪽 수, 저장장치, 네트워크 파일시스템인지.
1. **정규화를 확인한다(3NF).** 반정규화는 정규화된 모델에서 출발한다. 여기서 멈추지 않는다.
2. **용량을 산정한다.** 표마다 `행 크기 × 증가 속도 × 보관 기간`. 행 크기는 추측하지 않는다.
   합성 데이터로 DB 를 만들어 `sqlite_pages.py` 로 잰다(색인까지 합친 행당 바이트).
   시나리오는 셋(지금, 5배, 50배), 기간도 셋(1·3·5년).
3. **트랜잭션(질의) 유형을 목록으로 만든다.** 화면·API·배치·동기화에서 뽑는다.
   질의마다 누가, 얼마나 자주, 몇 행을 읽고 쓰는지, 목표 시간을 적는다. 이 목록이 물리 설계의 입력이다.
4. **물리 설계를 한다.** 질의마다 색인 경로를 정한다(등호 열 → 범위 열 → 정렬 열, 필요하면 덮는 색인).
   겹치는 색인을 뺀다. 행을 작게 만든다(해시는 BLOB, 시각은 INTEGER). 연결표는 WITHOUT ROWID.
   저널·동기화·트랜잭션 규칙을 정한다(`references/02`).
5. **반정규화를 판단한다.** 대상을 조사하고, 다른 방법(색인·질의·응용 로직)을 먼저 해 보고,
   그래도 목표를 못 맞출 때만 적용한다. 적용하면 **누가 맞추는지**(트리거, 쓰기 코드 한 곳, 배치)를 적는다(`references/03`).
6. **수명 주기를 정한다.** 표마다 언제 지우는지 적는다. 논리 삭제 행, 세션, 작업 기록, 로그.
   규칙이 없으면 "끝없이 커지는 표"라고 적는다.
7. **실측한다.** 합성 데이터로 N년치를 만들어 3의 질의 전부를 `explain_check.py` 로 잰다.
   합성 데이터는 실제 분포(길이, 편중, 유형 비율)만 따르고 실제 내용은 쓰지 않는다.
   목표를 넘는 질의가 있으면 4~5 로 돌아간다. **색인을 바꾼 뒤에는 질의 계획을 다시 본다**(아래 함정 첫 줄).
   커밋 비용은 **운영할 기계에서** `commit_bench.py` 로 잰다.
   동시 부하는 시간을 당겨 잰다. 30초마다 폴링하는 장치를 0.3초마다 돌리면 스레드 하나가 장치 100대쯤이다.
   실측 DB 는 스크래치에 만들고, 결과 파일(JSON·TXT)만 작업 폴더로 복사한다.
8. **운영 규칙을 적는다.** 통계(`PRAGMA optimize`), FTS `merge`·`optimize`, 백업, 무결성 검사.

## 판단 규칙

| 규칙 | 근거 |
|---|---|
| 느려지는 것은 대개 정규화가 아니라 **정렬·거르기를 색인이 못 받아 맞는 행 전부를 훑는 질의**다. 반정규화 전에 질의 계획부터 본다 | 색인이 있으면 조인은 행마다 log N. SQLite 는 작은 질의 여러 번도 싸다(`references/01`) |
| `ORDER BY … LIMIT n` 은 색인이 정렬을 받을 때만 n 에 비례한다. 못 받으면 맞는 행 수에 비례한다 | `USE TEMP B-TREE FOR ORDER BY` |
| 한 색인이 다른 색인의 앞부분이면 짧은 쪽을 지운다. UNIQUE 의 앞 열도 해당한다 | SQLite 질의 계획 문서 |
| 쓰기 트랜잭션은 `BEGIN IMMEDIATE` 로 연다 | 읽다가 쓰기로 올리면 busy_timeout 을 기다리지 않고 실패한다(실측 0 ms) |
| 쓰기가 잦고 읽기가 동시에 있으면 WAL + `synchronous=NORMAL` | 롤백 저널은 쓰는 동안 읽기를 막는다(실측 306번 중 261번) |
| 시각은 한 가지 형식으로. INTEGER UTC 초를 권한다 | 글자 형식을 섞으면 비교가 틀린다. 시간대가 모호해지지 않는다 |
| 사용자 입력은 FTS 질의에 그대로 넣지 않는다 | `v2.0`·URL·`-` 가 문법 오류를 낸다 |
| 끝없이 커지는 표는 설계 단계에서 삭제 규칙을 적는다 | 크기 문제의 대부분은 지우지 않는 표에서 온다 |
| 반정규화에는 "누가 맞추나" 가 함께 있어야 한다 | 맞추는 경로가 없으면 반정규화가 아니라 불일치다 |
| 두 표를 UNION 해 정렬하는 목록은 어떤 색인도 정렬을 받지 못한다. 늘 함께 보이면 슈퍼타입 한 표 + `(정렬 키, id)` 색인으로 | 실측: 링크 60만에서 87 ms 가 0.026 ms (`references/06`) |
| 끝까지 내려 더 불러오는 목록은 OFFSET 이 아니라 커서(마지막 행의 정렬 키·id 다음부터) | 새 행이 들어와도 중복·누락이 없고 뒤쪽 페이지도 같은 비용 |
| 멱등 키(해시)가 정당한 중복을 합치지 않는지 본다. 같은 파일 안에서 n번째 반복이면 입력 끝에 순번을 붙인다(첫 번째는 옛 값 그대로) | 유일본 DB 에서 합쳐진 행은 되돌릴 수 없다. 합성 180만 건에서 187건이 사라졌다 |

## 함정 (실제로 물린 것)

| 증상 | 대응 |
|---|---|
| 🔴 복합 색인 `(source_id, ts)` 를 더하고 `PRAGMA optimize` 를 돌린 뒤, 전체 타임라인이 0.06 ms 에서 549 ms 가 됐다. 플래너가 작은 표(채팅방 27행)를 바깥 반복에 두고 채팅방마다 읽은 행을 전부 정렬했다 | LIMIT 을 큰 표 한 곳의 서브쿼리 안에 둔다. 또는 `CROSS JOIN` 으로 큰 표를 바깥에 고정한다. 한 채팅방이면 번호를 먼저 구해 `source_id = ?`. 여러 채팅방이면 `INDEXED BY` 시각 색인 + CROSS JOIN, 또는 채팅방마다 LIMIT 을 걸어 합친다. 모두 0.03~0.25 ms 로 돌아왔다 |
| 파이썬 번들 SQLite 에 `dbstat` 가상 테이블이 없어 객체별 크기를 못 본다 | `scripts/sqlite_pages.py` |
| 색인 B-tree 의 잎만 세면 항목 수가 모자란다 | 색인 B-tree 는 내부 페이지 칸도 항목이다(표 B-tree 는 잎에만 자료) |
| 외부 콘텐츠 FTS5 의 `count(*)` 가 내용 표와 같아서 "동기화됨"으로 보였다 | `count(*)` 는 내용 표를 센다. `INSERT INTO f(f, rank) VALUES('integrity-check', 1)` 로 본다 |
| 요약 도구(WebFetch)가 trigram 토크나이저 도입 판을 3.43.0 이라고 옮겼다(실제 3.34.0) | 판·수치는 원문을 받아 직접 찾는다. 릴리스 노트로 확인한다 |
| 실측 DB 를 다시 만들려고 지우려다 막혔다(삭제 금지 프로젝트) | 실측 DB 는 스크래치에 새 이름으로 만든다. 도구는 임시 파일 없이 메모리에서 돈다(`commit_bench.py` 만 디스크가 필요해 자기가 만든 임시 파일을 쓰고 치운다) |
| 반정규화 후보를 먼저 떠올렸는데, 재 보니 셋 중 둘은 색인·질의 모양으로 풀렸다 | "다른 방법 먼저" 를 실측으로 한다. 두 안을 모두 만들어 같은 질의로 잰다(`references/03` §7) |
| 기본 설정(DELETE + FULL, 파이썬의 암묵적 BEGIN)에서 부하를 올리자 폴링이 잠금 대기 한도 5초까지 밀렸다. 오류는 0건이라 로그로는 안 보였다 | 오류 수가 아니라 p99·최대 지연을 본다. WAL + NORMAL + `BEGIN IMMEDIATE` 로 같은 부하가 p99 61 ms |
