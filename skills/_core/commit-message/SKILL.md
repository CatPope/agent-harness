# 커밋 메시지

## 모양

- 제목은 읽기 쉬운 것이 먼저다. 한 가지 일을 한 구절로 쓴다. 기호로 여러 일을 이어 붙이지 않는다.
- `내용 — 설명` 처럼 줄표로 설명을 잇지 않는다.
- 가운뎃점(`·`)을 쓰지 않는다. 나열은 쉼표나 "와" 로 한다.
- 본문은 `-` 로 시작하는 개조식으로 쓴다. 줄 끝은 명사형으로 맺는다. 추가, 수정, 누락, "~함" 같은 꼴이다.
- 길이와 타입 접두어는 저장소 관례를 따른다. 제목 50자, 빈 줄, 본문 한 줄 72자, 제목 끝 마침표 없음이 흔한 기준이다.

## 내용

1. **왜를 쓴다.** 무엇이 바뀌었는지는 diff 에 있다. 본문에 다시 풀어 쓰지 않는다.
2. **본문에 넣을 만한 것은 넷이다.** 해당하는 것만 쓴다.
   - 다른 변경의 준비 작업인지
   - 버그라면 증상과 오류 문구. 이슈 번호만 적지 않는다
   - 어느 커밋에서 생긴 틈인지. 내 실수면 내 실수라고 쓴다
   - 버린 대안과 맞바꾼 것
3. **설명이 안 되면 커밋하지 않는다.** 왜 필요한지 내 말로 못 쓰면 변경을 이해하지 못한 것이다. 다시 본다.
   쓰다가 더 나은 방법이 보이면 코드를 먼저 고친다.
4. **"또한", "추가로" 가 나오면 나눈다.** 한 커밋이 두 가지를 하고 있다.
5. **AI 가 쓴 코드도 커밋하면 내 것이다.** 왜 그렇게 정했는지 본문에 적을 수 있어야 한다.
   어느 부분에 AI 를 썼는지 적을지는 레포가 정한다. 그 레포의 `.gitmessage.txt` 에 그 줄이 없으면 적지 않는다.
6. 몇 달 뒤의 나나 다른 사람이 이 메시지만 보고 이해할 수 있는지 본다.
7. **검토를 거친 상태 그대로 커밋한다.** 커밋할 변경이 아직 검토 전인 다른 변경과 같은 파일에 섞여 있거나,
   그 변경을 불러와야 테스트가 돈다면 손으로 떼어 낸 변형본을 만들지 않는다. 변형본은 아무도 검토하지 않은
   코드다. 얽힌 쪽이 검토를 마칠 때까지 미루고 함께 커밋한다. 미룬 까닭은 작업 기록에 남긴다.

## 예시

값과 해시는 꾸민 것이다.

```
fix(ingest): 같은 줄이 두 번 나오면 순번을 붙여 보존

- 같은 파일에 똑같은 줄이 또 나오면 식별값이 겹쳐 둘째 줄이 누락
- "네" 같은 짧은 답이 같은 분에 두 번 찍힌 로그에서 확인
- a1b2c3d 에서 해시에 순번을 넣지 않은 내 실수
```

```
refactor(db): connect() 가 저널 설정을 받도록 변경

- 다음 커밋에서 서버 DB 를 WAL 로 열기 위한 준비
- 동작 변화 없음
```

```
feat(search): 두 글자 단위 색인 검색 추가

- "회의" 로 "주간회의를" 을 찾지 못하던 문제 해결
- 형태소 분석기는 외부 패키지가 필요해 쓰지 않음
- 색인 크기가 늘어나는 것은 감수
```

나쁜 예다. 둘째는 실제로 썼다가 고쳤다.

```
fix: 버그 수정
chore: 레포 뼈대 — 서버·PC 에이전트·명령행 구성과 두 DB 스키마
feat: 검색 추가 및 로그 정리 또한 설정 변경
```

## 템플릿

템플릿은 레포마다 둔다. 전역(`--global`)으로 걸지 않는다. 프로젝트마다 적을 것이 다르기 때문이다.

```bash
cp <이 스킬>/templates/gitmessage.txt <레포>/.gitmessage.txt     # 레포에 맞게 줄을 빼거나 더한다
git -C <레포> config --local commit.template .gitmessage.txt     # 클론마다 한 번
```

- `.gitmessage.txt` 는 레포에 커밋한다. 설정(`--local`)은 클론에 따라오지 않으니 README 에 위 둘째 줄을 적어 둔다.
- 레포에 `.gitmessage.txt` 가 있으면 그것이 그 레포의 기준이다. 템플릿에 없는 항목은 본문에 쓰지 않는다.
- `#` 으로 시작하는 줄은 메시지에 들어가지 않는다. `-m` 으로 넘기는 커밋에는 템플릿이 뜨지 않는다.
- VS Code 를 켜 둔 채 설정했으면 다시 켜야 적용된다.
