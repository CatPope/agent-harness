# 보고서 서식

## 왜 있는가

**서식 지적을 두 번 받았다. 두 번 다 같은 것이었다.**

```
1차   목차·말투가 제각각이다          → 고쳤다. 그런데 진행 문서에 한 줄만 남겼다
2차   제목이 난잡하다 · 글이 길다      → 규격이 문서로 없으니 다음 회차가 또 틀렸다
      글머리 기호가 없다
```

🔴 **1차 정정이 실패한 이유는 고친 결과만 남기고 규격을 남기지 않은 것이다.**
*"형식에 맞췄다"* 는 기록은 **무엇에 맞췄는지**를 남기지 않는다. 다음 회차는
그 문장을 읽어도 무엇을 해야 할지 알 수 없다.

**그래서 이 스킬이 규격 정본이다.** 고친 사례가 아니라 지켜야 할 것을 적는다.

## 착수 전 — 이것을 건너뛰면 나머지가 소용없다

🔴 **새 보고서를 백지에서 쓰지 않는다. 직전 회차 보고서를 먼저 연다.**

```bash
ls -t <보고서 폴더>/*.md | head -3          # 최근 것 세 개
grep -E "^#{1,3} " <직전 보고서>            # 제목 골격을 본다
```

서식은 **앞선 산출물 안에 있지 문서 설명 안에 있지 않다.** 열지 않고 쓰면
매번 새로 발명하게 되고, 매번 조금씩 달라진다.

## 규격

### 1. 제목 — 대시를 넣지 않는다

🔴 **제목에 `-` `–` `—` 를 쓰지 않는다.** 설명을 덧붙이고 싶어지면 그 제목이
너무 긴 것이다. **명사구 한 덩어리**로 끊는다.

```
✗  ## 1. 한눈에 — 무엇을 하려는 것인가
✓  ## 1. 개요

✗  ## 5. 해석 — 변경된 촬영 환경이 주는 이점
✓  ## 5. 촬영 환경이 주는 이점

✗  ### 2.1 정의 — 가장 가까운 이웃을 보고 판단함
✓  ### 2.1 정의
```

덧붙이려던 설명은 **제목 아래 첫 줄**로 내린다. 그 자리가 원래 그것의 자리다.

### 2. 문단 — 1~2줄

🔴 **한 항목은 1~2줄.** 서술형 문단을 쌓지 않는다. 읽는 사람은 회의 중에 훑는다.

```
✗  네댓 줄짜리 문단이 절마다 서너 개
✓  핵심 한 줄  +  근거 한 줄
```

### 3. 글머리 기호를 쓴다

🔴 **문단 세 개가 나란히 서면 글머리 기호로 바꾼다.** 줄글이 이어지면
어디가 항목의 경계인지 보이지 않아 난잡해진다.

```markdown
- **결론.** 한 줄로 먼저 말한다.
- 근거는 그 다음 줄에.
```

표와 코드 블록은 이미 항목이 갈려 있으므로 그대로 둔다.

### 4. 이모지를 넣지 않는다

🔴 **보고서 본문에 이모지를 쓰지 않는다.** `🔴` 도 이모지다.
강조는 **굵은 글씨**로 한다.

> ⚠️ 이 규칙은 **사람에게 제출하는 보고서**에만 해당한다.
> 작업 문서·스킬·진행 기록은 별개다(아래 §적용 범위).

### 5. 말투 — 항목명은 명사형, 설명은 「~한다」

🔄 **2026-10-28 사용자가 바꿨다:** *"소제목 명사형, 설명 ~한다"*, 보고서도 *"~한다로 바꿔줘요."*
(10-08 의 「~임 / ~함 / ~음」 명사 어미 규칙을 대신한다.)

🔴 **제목·소제목·글머리 항목명은 명사형, 그 아래 설명 문장은 동사형 평서 어미("~한다 / ~했다 / ~이다")로 맺는다.**
「~함」「~음」「~임」으로 맺지 않는다. 본문 문장, 글머리 설명, **표 칸 안의 문장까지** 같다. 보고서 전체가 같은 말투여야 한다.

```
ㅇ 파일 전달 및 수신                                   ← 항목명: 명사형
  - 웹에서 파일을 올리고 받을 PC를 고르면, 해당 PC의 에이전트가 30초 안에 받아 프로젝트 폴더에 저장하고 서버에 알린다.
  - 꺼진 PC로 보낸 파일은 7일 동안 대기열에 둔다.

✗  후보는 공식 모델이 있는 것 위주로 고름.          ✓  후보는 공식 모델이 있는 것 위주로 골랐다.
✗  공식 페이지에서 확인하지 못함.                   ✓  공식 페이지에서 확인하지 못했다.
✗  (표 칸) 공식 폴더에 없음                         ✓  (표 칸) 공식 폴더에 없다
```

- 표 칸이 문장이 아니라 낱말·명사구(「완료」「결정 대기」「사내 VM」)면 그대로 둔다. 문장일 때만 「~다」로 맺는다.
- 평가 기준표의 질문("~있는가")은 질문이므로 그대로 둔다.
- 이미 「~함」으로 낸 보고서·구글독스 탭은 이 규칙 때문에 다시 고쳐 올리지 않는다. 앞으로 쓰는 것부터 적용한다.
- 다 쓴 뒤 남은 「~함 / ~음 / ~임」 종결을 센다(아래 §검토).

### 6. 절 골격

```
1. 개요          무엇을 왜 했는가
2. 조건          전제 · 대상 · 환경
3. 결과          측정값 · 확인한 것
4. 해석          그래서 무엇을 뜻하는가
5. 제약          확인하지 못한 것 · 한계
6. 제안 사항     다음에 할 일
7. 관련 소스     경로 · 실행 명령
```

**절 이름은 주제에 맞게 바꾸되 순서와 개수는 유지한다.** 골격이 같아야
여러 회차를 나란히 놓고 비교할 수 있다.

### 7. 머리표와 첫 줄

```markdown
# ① [주제]

<회의명/날짜 한 줄>

| 문서 종류 | … |
|---|---|
| 작성일자 | … |
| 작성자 | … |
| 대상 | … |
```

여러 건을 한 회의에 낼 때는 **`① [주제]` 형식**으로 번호를 단다.
번호는 **제출 순서**를 따르며 원래 안건 번호가 아니다.

🔴 **머리 메타줄(작성일 · 작성자 · 버전 · 보고서 종류)은 md 에만 둔다. 구글독스에는 올리지 않는다.**
2026-10-08 에 사용자가 구글독스 탭 두 개에서 이 줄을 직접 지우고 *"구글독스에는 해당 부분 올리지 마세요"* 라고 했다.
업로드 변환기가 이 줄을 건너뛴다(예: 프로젝트의 `_upload_1008_to_gdocs.py` 의 `META_LINE`).

## 검토 — 눈으로 보지 말고 센다

제출 직전에 돌린다. **보고서마다 따로가 아니라 전부 한 번에** 돌린다.

```bash
for f in <보고서들>; do
  printf "%-44s 제목 %2s · 불릿 %3s · 이모지 %2s\n" "$f" \
    "$(grep -cE '^#{1,4} ' "$f")" \
    "$(grep -c '^- ' "$f")" \
    "$(grep -coP '[\x{1F300}-\x{1FAFF}\x{2600}-\x{27BF}]' "$f")"
done
```

남은 「~함 / ~음 / ~임」 종결(§5)도 센다. 주소가 든 줄은 뺀다.

```python
import re
for i, l in enumerate(open(path, encoding="utf-8"), 1):
    if "http" in l: continue
    for m in re.finditer(r"(\S*(?:함|음|임))(?=[.)]|\s*\||\s*$)", l.rstrip()):   # 명사형 낱말(「결과 수신함」 같은)은 눈으로 거른다
        print(i, m.group(1))
```

제목 속 대시는 바이트 범위 문제로 `grep -E "[-–—]"` 가 **오탐한다.**
문자 단위로 세야 한다.

```python
import re
DASH = set("-–—‒―−")
for ln in open(path, encoding="utf-8"):
    if re.match(r"^#{1,6} ", ln) and DASH & set(ln):
        print("대시:", ln.strip())
```

🔴 **내부 일관성만 보면 통과한다.** 네 건이 똑같이 틀려도 "전부 같다" 는
나온다. **반드시 규격과 대조한다** — 기준은 이 문서이지 옆 문서가 아니다.

## 적용 범위

| 대상 | 이 규격 | 이유 |
|---|---|---|
| 사람에게 제출하는 보고서 | **적용** | 읽는 사람이 회의 중에 훑는다 |
| 작업 문서 · 진행 기록 | 적용 안 함 | 강조 표시가 우선순위 신호로 굳어져 있다 |
| 스킬 | 적용 안 함 | 같은 이유 |

**범위를 임의로 넓히지 않는다.** 작업 문서의 표시를 걷어내면 다음 세션이
무엇이 중요한지 읽지 못한다.

## 하지 않는 것

- 규격을 고친 결과만 기록하고 규격 자체를 안 남기지 않는다 — **1차 실패의 원인이다**
- 지적받은 항목만 고치지 않는다 — 같은 성질의 다른 위반도 함께 센다
- 분량을 줄이면서 수치·출처를 빼지 않는다 — 줄일 것은 **설명 문단**이다
