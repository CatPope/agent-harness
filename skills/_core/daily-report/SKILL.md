# 일일 업무보고 작성 (시간대별 양식)

**읽는 사람은 블록마다 "이 시간에 무엇을 했나"를 본다.** 업무내용 한 줄만 읽고 한 일이 보여야 한다.

이 스킬은 절차와 규칙만 담는다. 회사 시스템에 올리는 스크립트, 근무시간, 양식 예시는 환경마다 달라
설치처의 `기록/` 폴더에 둔다(아래 "설치처에 두는 것").

## 설치처에 두는 것

| 파일 | 내용 |
|---|---|
| `기록/양식_일일.md` | 🔴 서식의 정본. 아래 규칙과 부딪히면 이 파일을 따른다 |
| `기록/양식_주간.md` | 주간보고 서식 |
| `기록/작성_설정.md` | 근무시간, 점심시간, 휴가 처리 방식 |
| `기록/세션_설정.json` | 참여 세션 목록(`participants`), 관리 세션 이름, 취합 에이전트 모델 |
| `기록/피드백_반영.md` | 사용자가 승인한 개선 사항. 에이전트는 읽기만 한다 |

상사가 바뀌어 양식이 바뀌면 사용자가 새 예시를 주고, 관리 세션이 이전 양식을 `보관/` 에 옮긴 뒤
양식 파일만 고친다. 에이전트는 실행 때마다 읽으므로 다음 실행부터 적용된다.

## 1. 🔴 업무내용에 한 일이 드러나야 한다

**대상과 행위가 둘 다 있어야 한다.** 서술어(작성, 수정, 확인, 진행)를 지웠을 때 남는 말이 없으면
대상이 빠진 것이다.

| 안 됨 | 됨 |
|---|---|
| `문서 작성` | `공통코드 대상 범위 검토서 작성(해외 활용 사례)` |
| `오류 수정` | `알림톡 발송 오류 수정` |
| `학습 진행` | `공 차기 조건 추가 재학습` |
| `회의` | `월간보고 회의 참석` |

- 🔴 **짧게 쓴다.** `대상 + 행위` 한 덩어리면 족하다(`ETL 오류 수정`, `ETL 매뉴얼 작성 계속`).
  조건, 수치, 결과 설명은 빼고, 꼭 필요하면 괄호 하나만 붙인다
- 며칠 이어지는 일은 그날 나아간 부분을 쓴다(`국내 사례 작성` → 다음 날 `해외 사례 작성`).
  같은 줄을 날마다 반복하면 진척이 안 보인다. 유지보수처럼 같은 일이 이어지면 `작성 계속` 으로 밝힌다
- 우리끼리 붙인 이름(단계 약칭, 옵션명, 파일명, 영문 약어)은 풀어 쓴다. 회사 공식 명칭과 시스템명은
  그대로 쓴다. 이 점검은 다 쓴 뒤 따로 한다. 쓰는 중에는 눈에 안 띈다
- 지시하고, 만들고, 검수하는 과정은 한 일로 묶는다. `지시서 발행`, `결과 검수` 같은 줄을 따로 세우지 않는다
- 하려던 일, 다음에 할 일을 한 일처럼 쓰지 않는다

## 2. 🔴 시간 블록

- 🔴 **근무시간에 빈 시간이 있으면 안 된다.** 점심만 비운다. 휴가, 외근은 `휴가`, `외근(장소)` 블록으로 쓴다
- 🔴 **시간이 겹치면 안 된다.** 두 프로젝트 일을 실제로 동시에 했어도 시간을 나눠 한 블록에 한 일만 쓴다
- 🔴 **같은 프로젝트 일은 시간대를 붙인다.** 실제 순서가 오락가락했어도 `[A] [A] [A] [B] [B]` 처럼 모은다.
  점심 앞뒤로 나뉘는 것은 괜찮다
- 🔴 **사용자가 직접 한 일(회의, 발표, 면담)이 먼저 자리를 잡는다.** 그 시각을 고정하고 남은 시간을 프로젝트 일로 채운다
- 블록 경계는 점심 시작에 끝나고 점심 끝에 시작한다. 시간은 30분 단위로 맞춘다
- 근무시간 밖에 저절로 돈 일(밤새 돈 학습, 예약 작업)은 블록을 따로 만들지 않는다. 그 결과를 근무시간에 확인하거나 정리한 일로 쓴다
- 근거가 있는 업무로 시간을 채운다. 근거가 없는 시간대가 남으면 지어내지 말고 사용자에게 묻는다
- 회사가 업무로 보지 않는 일(개인 학습 과정 등)은 쓰지 않는다. 그 안에서 상사 지시로 모인 회의, 발표만 그 시간만 쓴다

### 프로젝트 태그

🔴 **모든 줄에 붙인다.** 어느 프로젝트에도 속하지 않는 일(전사 회의, 교육 참석)은 `[기타]` 를 붙인다.

## 3. 🔴 여러 프로젝트면 각 세션의 작업 기록을 모아서 쓴다

사용자는 프로젝트마다 다른 Claude 세션을 쓴다. 한 세션은 자기 프로젝트 일만 안다. 혼자 쓰면 다른 프로젝트
시간이 빠지거나 겹친다. **참여 세션 몫은 그 세션이 정리한 작업 기록에서 가져온다.**

🔴 **세션과 문답하지 않는다.** 메시지마다 그 세션의 사용량이 든다.

```
1. 열린 세션에 "작업 정리" 요청을 한 통만 보낸다. 되묻기, 합의안 검토, 끝 인사는 없다
2. 세션은 compact·clear 때 쓰는 정리 스킬 [[compact-checkpoint]] 의 '일일보고 작업 정리 요청' 절차로 정리한다.
   정리 기준을 하나로 두기 위해서다. 답은 반드시 한 줄이다:
   "금일 작업 업데이트 완료: <파일 경로>" 또는 "금일 진행 내용 없음"
3. 닫힌 세션은 스크립트가 원본 세션을 백그라운드로 열어(claude -p --resume <세션 ID>) 같은 정리를 시킨다.
   답이 없거나 정해진 시간 안에 끝나지 않으면 그 세션의 메모리 폴더와 그날 바뀐 파일을 직접 본다
4. 받은 파일에서 그날 부분만 읽어 블록을 만든다. 정할 수 없는 것은 묻지 않고 '사용자 확인 필요' 에 올린다
5. 취합한 쪽이 저장하고 사용자에게 낸다. 저장한 것이 "일일보고를 했다" 는 작업 기록이다
```

- 🔴 **다른 세션의 대화 기록은 읽지 않는다.** 취합·주간보고 에이전트는 대화 기록 파일, 세션 관리 도구의 파일,
  다른 세션 맥락을 읽는 스킬이 권한으로 막혀 있어야 한다
- 셸은 읽기 명령만 쓴다(`find`, `stat`, `ls`). 파일 수정 시각을 근거로 쓰기 위해서다
- 🔴 **같은 세션을 두 곳에서 열지 않는다.** 프로세스가 살아 있는 세션은 백그라운드로 열지 않고 메시지로만 요청한다.
  두 곳에서 열면 사용량이 늘고 기록이 갈라진다
- 세션은 세션 ID → 이름 → 작업 폴더 순으로 찾는다. 폴더 이름으로 찾지 않는다 — 한글 폴더는 프로젝트 기록 폴더 이름이
  `-` 로 뭉개져 겹친다
- `/clear` 를 하면 세션 ID 는 바뀌고 이름은 새 ID 로 옮겨 간다
- 🔴 **Claude 설정 폴더가 여럿일 수 있다.** 계정을 여럿 쓰는 도구는 계정마다 설정 폴더(`CLAUDE_CONFIG_DIR`)를 따로 둔다.
  열린 세션 판정은 모든 설정 폴더의 `sessions\` 를 보고, 닫힌 세션은 기록이 가장 최근에 쓰인 폴더로 연다.
  한 곳만 보면 열린 세션을 닫힘으로 보고 또 열거나, 옛 사본을 읽어 "진행 내용 없음" 으로 답한다
- 백그라운드로 연 세션은 정리 스킬이 고치는 곳(작업 폴더, 메모리 폴더, 스킬 폴더)만 고친다. 복제본이 아니라 원본을 열어야
  정리 내용이 그 세션 대화에 남는다

### 참여 세션 = 사용자가 넣으라고 한 세션

사용자가 "일일보고에 X 넣어/빼" 라고 할 때만 관리 세션이 `세션_설정.json` 의 `participants` 를 고친다(백업 뒤).
항목은 `name`(세션 이름), `tag`, `dir`(작업 폴더), `session_id`. 실행 때는 이 목록만 쓴다.
세션 관리 도구의 화면 연결(캔버스 선 등)로 자동으로 맞추지 않는다. 도구를 바꾸면 목록이 통째로 흔들린다.

- 회사가 금지한 프로젝트는 참여에서 빼고, 보고에도 쓰지 않는다
- 다른 세션의 대화 내용은 설정에 옮기지 않는다. 이름, 폴더, ID 만 쓴다

### 정해진 시각 자동 작성

작업 스케줄러가 근무 끝 무렵에 취합 스크립트를 부른다. Claude Code 가 안 켜져 있어도 돈다.

```
목록    세션_설정.json 의 참여 세션
제출본  지난 2주 평일 제출본을 회사 시스템에 올라간 판으로 다시 맞춘다
확인    세션마다 열림·닫힘과 메모리 폴더를 본다
정리    닫힌 세션은 원본을 백그라운드로 열어 작업 정리 요청
요청    열린 세션에만 작업 정리 요청 한 통
모으기  받은 파일, 닫힘·무응답 세션은 메모리 폴더와 그날 바뀐 파일
쓰기    이 스킬 규칙, 양식 파일, 피드백_반영.md 대로. 모르는 것은 '사용자 확인 필요'
저장    날짜별 보고 파일(완료 신호)과 주 기록 파일 끝에 초안 절
검토    검토 화면에서 사용자가 반려(사유 → 고친 새 판) 또는 직접 고쳐 통과 → 회사 시스템에 올린다
```

- 사용량이 모자라면 사용자가 자동 실행을 끈다. 켜고 끄는 것은 사용자가 정한다
- 근무 끝 전에 돌면, '진행 중' 으로 적힌 일이 근무 끝까지 이어진다고 보고 마지막 블록을 늘리고 '사용자 확인 필요' 에 올린다
- 🔴 사용자가 직접 한 일(회의, 발표, 외근, 휴가, 메일 업무)은 사용자 일정을 맡은 세션의 기록이 먼저 자리를 잡는다
- 🔴 앞 날짜는 **실제로 제출된 판**을 근거로 본다. 사용자가 초안을 고쳐 내는 일이 많다. 자동 초안은 제출본이 없을 때만 쓴다
- 🔴 취합 에이전트는 사용자 창구가 없다. 특이사항(응답 없음, 근거 부족, 규칙 충돌, 권한 막힘, 오류)은 파일에 적고
  관리 세션에 메시지 한 통으로 보고한다. 관리 세션이 사용자에게 전한다
- 정리 요청 때 각 세션은 남은 작업 파일의 '## 차주 추진 예정 (일일보고용)' 절도 갱신한다. 주간보고 차주는 이 절만 본다
- 종일 휴가인 날은 쓰지 않는다. 반차는 휴가 시간을 블록에서 뺀다. 휴가가 겹치거나 이어지면 합친 뒤 판단한다
- 결과는 초안이다. 사용자 답을 받아 고친 뒤 낸다

### 중단되면 다음 평일 아침에 이어 쓴다

사용량 한도 등으로 멈추면 완료 신호(날짜별 보고 파일)가 없다. 다음 평일 아침 예약 작업이 지난 평일 중
실행은 시작했는데 결과가 없는 날을 다시 돌린다. 시작 판정은 실행로그의 '취합 에이전트 시작' 줄로 한다
(시험 실행도 실행로그를 남기므로 파일 유무로 보지 않는다).

## 3-1. 주간보고

일일보고를 모아 주간보고를 쓴다. 정해진 요일의 일일보고를 회사 시스템에 올린 뒤에 돌린다.
정해진 시각에 따로 돌리면 그 주 마지막 일일보고가 초안인 채로 들어간다.

```
범위    그 주 월요일 ~ 실행한 날
금주    날마다 일일보고를 읽는다. 판 우선순위: 제출본 > 주 기록의 확정안 > 자동 초안
차주    각 프로젝트 남은 작업 파일의 '## 차주 추진 예정 (일일보고용)' 절만 읽는다(사용량 절약).
        사용자가 허락하면 '(제안, 사용자 확인 전)' 줄도 넣는다. 빼면 차주가 늘 빈다
서식    기록/양식_주간.md
```

- 세션과 메시지를 주고받지 않는다. 대화 기록은 읽지 못한다
- 일일보고보다 구체적으로 쓴다. 며칠 이어진 일은 한 줄 아래에 단계별 줄을 둔다
- 다시 돌릴 때는 이전 판의 원고와 검토 상태 파일을 **둘 다** 옮긴다. 하나만 남으면 화면이 옛 판을 읽는다

## 3-2. 🔴 개선은 제출본 대조와 사용자 승인으로만 한다

```
1. 사용자가 실제로 낸 보고를 관리 세션에 주면 제출본으로 저장한다
2. 관리 세션이 초안과 제출본을 비교하고 사용자 피드백과 함께 개선안을 사용자에게 올린다
3. 사용자가 승인한 것만 피드백_반영.md 에 적는다(양식이 바뀐 것이면 양식 파일을 고친다)
4. 취합·주간보고 에이전트는 실행 때마다 피드백_반영.md 를 읽고 지킨다. 에이전트는 이 파일을 고치지 않는다
```

## 4. 근거 찾는 순서

```
① 그 세션이 정리한 작업 기록 파일     세션이 직접 적은 것이라 가장 정확하다
② 프로젝트의 메모리 폴더             완료 로그와 남은 작업 파일
③ git log --since=<날짜>            실제로 커밋된 것
```

## 하지 않는 것

- 원인 분석, 기술 판단, 수치 나열을 넣지 않는다. 분량을 보여 주는 괄호 하나면 족하다
- 누가 무엇으로 했는지(에이전트, 도구 이름) 쓰지 않는다
- 근무시간 밖 블록, 겹치는 블록, 근거 없는 블록을 만들지 않는다
- 참여 세션의 작업 기록을 보지 않고 여러 프로젝트 보고를 확정하지 않는다
- 다른 세션의 대화 기록을 읽지 않는다
- 사용자가 말하지 않은 개선점을 짐작해 고치지 않는다. 다음 보고 때 먼저 묻는다
- 🔴 세션 기록(jsonl)을 읽는 스크립트는 파일을 열어 둔 채 두지 않는다. 공유 모드(ReadWrite|Delete)로 열고 바로 닫는다.
  PowerShell `[IO.File]::ReadLines` 를 중간에 끊으면 파일이 닫히지 않아, 실행 중인 세션이 기록을 쓰지 못했다(며칠치 대화 손실)
- 🔴 Windows 에서 `os.kill(pid, 0)` 으로 살아 있는지 보지 않는다 — 프로세스를 종료한다. OpenProcess + GetExitCodeProcess 로 본다
- 🔴 스크립트에서 pwsh 를 띄울 때 DETACHED_PROCESS(0x8)를 쓰지 않는다. 스토어판 pwsh 가 아예 실행되지 않았다.
  CREATE_NEW_PROCESS_GROUP|CREATE_NO_WINDOW(0x200|0x08000000)만 쓴다
- 검토 서버는 포트를 혼자 쓰게 연다(Windows `SO_EXCLUSIVEADDRUSE`). 같은 포트에 서버 둘이 떠 옛 코드가 요청을 받은 적이 있다
