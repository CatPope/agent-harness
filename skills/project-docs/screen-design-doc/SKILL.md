# 화면설계서 쓰기

## 왜 있는가

2026-09-26 에 디자이너에게 보여 줄 화면설계서 초안을 처음 만들었다. 사용자가 양식과 가이드 글 세 편을 주고
"작성법을 숙지하고 스킬로 남기라" 고 했다. 이 스킬은 그 세 편을 하나로 합친 것이다. 셋은 같은 문서를 다른 쪽에서 설명한다.

## 들어 있는 것

| 경로 | 내용 |

| `scripts/e2e_test.py` | 데모 클릭 시험. 예시는 43개 항목 |

처음 한 번 `setup.ps1`(윈도) 또는 `setup.sh` 를 돌린다. python-pptx, Pillow, Playwright 와 Chromium 을 깐다.

원래 양식에서 레퍼런스가 부족한 장에만 실제 사례를 붙인다(사용자 09-28). User flow·Logic process 는 양식 4~5장의 예시로 충분하다.
UI 설계는 양식 7장이 빈 틀뿐이라, 캡처 번호와 Description 번호가 1:1 로 맞는 실제 장 하나를 붙였다.
산출물 전체(예시 프로젝트는 52장)를 넣지 않는다. 전체와 클릭 데모는 `build.py` 로 다시 만든다.
`build.py` 는 양식 장을 자리가 아니라 역할로 찾는다. 제목 슬라이드, 제목이 History·서비스 개요인 장, 첫 Description 장을 본보기로 쓰고
나머지 양식 장(예시 장 포함)은 뺀다. 예시 장을 떼어 낸 yamestyle 원래 양식(7장)을 `TEMPLATE` 로 줘도 같은 결과가 나온다.

🔴 **양식 고르는 순서.** 사용자가 따로 준 양식이 있으면 그것을 쓴다. `templates/` 의 양식은 사용자 양식이 없을 때만 쓴다.
먼저 사용자에게 받은 양식이 있는지 확인하고, 있으면 생성기에 환경 변수 `TEMPLATE` 로 그 경로를 준다.
생성기는 양식의 구조(본보기 문단·표·도형 번호)를 전제한다. 다른 양식이면 구조를 먼저 덤프하고 생성기를 맞춘다.

## 양식 파일의 구조

양식은 16:9(338.7 × 190.5 mm) PPTX 이고 슬라이드 마스터에 레이아웃 4개가 있다. 장표를 늘릴 때는 레이아웃을 골라 새로 만든다.

| 레이아웃 | 쓰는 장표 | 채울 곳 |
|---|---|---|
| 제목 슬라이드 | 표지 | 제목, 버전, 작성일, 작성자. 가운데 Confidential 상자는 레이아웃에 있다 |
| Summary | History, 서비스 개요, 화면 목록, 공통 가이드, User flow, Logic process | 제목과 자유 영역. 표는 양식 예시 장표의 표를 복제해 쓴다 |
| 사용자 지정 레이아웃 | 메뉴 그룹 구분 | 그룹 이름, 그 아래 수록 내용 한두 줄 |
| Description | UI 설계 | 위쪽 Page Title, Group Title. 왼쪽 약 240 mm 가 화면 자리, 오른쪽 94 mm 가 Description 표 |

Description 표는 `Summery.` 머리 한 줄, 요약 칸 한 줄, 번호 칸 7줄이다. 양식 철자 Summery 는 원본 그대로 둔다.
글자는 머리 9pt 굵게, 본문 8pt, 번호 8.5pt 다. 번호가 7개를 넘으면 행을 늘리지 말고 화면을 둘로 나눈다.

## 장표 순서와 쓰는 법

1. **표지.** 문서 이름, 버전, 작성일, 작성자.
2. **History.** 버전, 날짜, 바뀐 내용, 바뀐 페이지, 작성자. 고칠 때마다 한 줄을 더한다. 파일 버전 규칙(`_vX.Y.Z`)과 같은 번호를 쓴다.
3. **서비스 개요.** 기획배경, 기획목적(정성), 기대효과(목적을 수치로), 기능요약, 기타사항. 개요만 읽어도 방향이 전해져야 한다.
   아래 기획일정 표는 WBS 가 따로 있으면 WBS 를 가리키는 한 줄로 줄인다.
4. **화면 목록.** 화면 ID, 화면명, 그룹, 플랫폼, 관련 요구사항, 데모 포함 여부. IA 가 트리라면 이 표는 개발 단위 목록이다.
   양식에는 없지만 sooya14 가 권하고, 디자이너가 전체 규모를 먼저 본다.
5. **공통 가이드.** 여러 화면에 반복되는 것을 앞에 한 번만 정한다. 내비게이션, 팝업 유형, 알림 정책, 역할별 분기, 상태 화면(로딩·빈 목록·오류), 용어.
6. **User flow.** 단위 서비스마다 한 장. STEP 열로 나눈 표 안에 시작, 처리, 판단, 연결점, 끝을 그린다. 흐름의 윤곽만 보인다.
7. **Logic process.** 판단과 데이터 저장이 많은 흐름만 따로 그린다. 입력 항목, 판단 기준, 실패했을 때 어디로 가는지, 어느 DB 에 쓰는지.
   개발과 QA 가 이 장을 기준으로 본다. 부실하면 개발자가 "이거 이렇게 되는 게 맞아요?" 라고 묻는다.
8. **메뉴 그룹 구분.** 그룹이 바뀔 때 한 장. 그룹 이름은 뒤따르는 UI 설계 장의 Group Title 과 같게 쓴다.
9. **UI 설계.** 왼쪽에 와이어프레임, 요소에 ①②③ 번호, 오른쪽 Description 에 번호별 설명.

## 와이어프레임 규칙

- 선, 면, 글자로만 그린다. 색, 그림, 세밀한 장식은 디자이너의 작업을 막는다(yamestyle).
- 클릭 데모에서 캡처할 때는 흑백 와이어프레임 모드로 찍는다. 데모는 색을 쓰고, 설계서는 쓰지 않는다.
- 번호는 화면 위 요소 옆에 작은 원으로 붙이고, Description 의 번호와 1:1 로 맞춘다.
- 같은 화면이라도 역할이나 상태에 따라 달라지면 케이스별로 장을 나눈다. 목업과 인터랙션은 케이스마다 분리한다.

## Description 쓰는 법

- 요약 칸에는 화면 ID, 이 화면이 하는 일 한 문장, 관련 요구사항 ID 를 적는다.
- 번호 칸 하나에 한 가지만. 무엇이 보이는지, 누르면 무엇이 되는지, 어떤 조건에서 달라지는지.
- 정렬 기준과 노출 순서를 적는다. 예: "최신순", "마감 임박 순".
- 분기처리: 로그인 여부, 역할(관리자·팀장·부팀장·회원)에 따라 다르게 보이는 것.
- 예외처리: 값이 없을 때(빈 목록, 미입력), 실패했을 때(전송 실패, 업로드 중단).
- 유효성 체크: 필수 입력, 형식, 길이, 중복. 고정 영역과 데이터에서 불러오는 가변 영역을 구분한다.
- 역할 이름은 설명 글과 화면 글자를 나눈다. 예시 프로젝트는 설명 글에 서비스 관리자(앱 안 역할)와 시스템 관리자(서버·DB 담당)를 쓰고, 화면 글자는 관리자로 두었다.
- 정해지지 않은 것은 비워 두지 않는다. "회의 뒤 기재", "미정(FR-05)" 처럼 적고 History 로 버전을 올린다.
- 개발자와 디자이너가 물을 질문을 먼저 떠올리고 그 답을 적는다.

## 클릭 데모와 같은 원본에서 만들기

화면설계서와 클릭 데모 HTML 을 한 원본에서 만든다. 발표자는 PPT 로 설명하고, 팀원은 HTML 을 직접 눌러 본다. 예시 구현이 `scripts/` 에 있다.

| 파일 | 역할 |
|---|---|
| `scripts/spec.json` | 정본. 화면 ID, 그룹, 제목, 요약, 요구사항, 번호별 설명, 흐름, 공통 가이드 |
| `scripts/demo.html` | 데모 원본. 요소에 `data-d="번호"`. `/*SPEC*/` 자리에 spec 이 들어간다 |
| `scripts/extra.html` | 데모에 넣지 않는 참고 화면(디스코드 결과, 휴대폰 알림, 공통 팝업, 상태 화면 등). 캡처 전용 |
| `scripts/build.py` | ① spec 을 넣어 데모 HTML 저장 ② Playwright 로 화면마다 흑백+번호 모드 캡처 ③ 양식 PPTX 에 채워 저장 |

```bash
python <스킬>/scripts/build.py 1.0.0     # 실행 폴더의 out/ 에 같은 버전의 html 과 pptx (OUT_DIR 로 바꾼다)
python <스킬>/scripts/e2e_test.py        # out/ 의 가장 최근 데모를 눌러 본다
```

- 데모는 `#화면ID` 로 바로 열리고, `?wire&marks` 를 붙이면 캡처 모드가 된다.
- 설명 보기 버튼을 켜면 데모에서도 번호와 Description 이 보인다. 설계서와 같은 글이다.
- 데모에 없는 화면도 설계서에 들어갈 수 있다. 앱 밖에서 일어나는 결과(디스코드 공지방, 휴대폰 알림), 여러 화면이 함께 쓰는 팝업과 상태 화면이 그렇다.
- 고칠 때는 spec 과 데모를 고치고 다시 생성한다. PPTX 를 손으로 고치면 다음 생성에서 사라진다.

## 여러 기기에서 도는 화면 (2026-09-27)

- 데모의 틀(스마트폰 앱, PC 앱, 웹)은 화면과 따로 고른다. `?dev=mob|pc|web` 로 캡처한다. PC 앱과 웹은 왼쪽 메뉴, 스마트폰은 하단 탭.
- UI 설계 장은 기본으로 스마트폰과 웹 캡처를 나란히 싣는다. 기기마다 동작이 다른 화면(자료 올리기)만 PC 앱을 따로 싣는다. 구성은 `build.py` 의 `SHOTS`.
- 캡처 전에 `document.fonts.ready` 를 기다린다. 웹 글꼴이 늦게 오면 번호 상자가 요소에서 밀린다.
- 흑백 필터는 번호 배지까지 회색으로 만든다. 배지는 필터 밖(#device)에 둔다.
- 역할이 겹치면(서비스 관리자 + 팀장) 팀 역할 하나와 권한 표시를 따로 둔다. 자기 관리자 권한은 스스로 못 풀게 한다.

## 쓰는 순서

1. 요구사항서의 기능 요구사항(FR)을 화면으로 나눈다. 모든 필수 FR 이 적어도 한 화면에 걸려야 한다.
2. 화면 목록과 User flow 를 먼저 쓴다. 흐름에서 빠진 화면이 여기서 보인다.
3. 공통 가이드를 정한다. 팝업과 상태 화면을 여기서 정해 두면 화면마다 반복하지 않는다.
4. 데모를 만들고 화면마다 번호를 붙인다. Description 을 쓴다.
5. 생성하고, 슬라이드를 PNG 로 뽑아 눈으로 본다. 번호가 요소 위에 제대로 앉았는지, 표 글이 넘치지 않는지.
   양식의 빈 표 행(History 등)은 글자 크기와 정렬이 들어 있지 않다. 채우면 기본 18pt 로 커지고 열 정렬이 어긋난다.
   생성기가 첫 행과 같은 크기·정렬을 준다. 파일 속성만 봐서는 안 보이고 렌더해야 보인다.
6. FR 추적을 대조한다. 화면 목록의 요구사항 열에 없는 필수 FR 이 있으면 빠진 것이다.
7. 사람이 읽는 문서이므로 [[plain-writing]] 의 `check_tone.py` 로 spec 의 글을 검사한다.

## 관계

- 화면 디자인 원칙: [[ui-design-principles]]. 데모의 색과 배치는 그 스킬을 따른다.
- 문장 규칙: [[plain-writing]]. 양식이 정한 형식(Summery, 번호 칸)은 문장 규칙보다 우선한다.
- 요구사항 원본: [[planning-docs]] 의 `scripts/req_build.py` 의 `BODY`. `build.py` 가 필수 FR 이 화면에 모두 걸렸는지 여기서 읽어 본다. 다른 파일이면 환경 변수 `REQ_BUILD`.
