# 보고서 쓰기

## 왜 있는가

2026-09-25 에 보고서를 여섯 건 썼다. 종류가 제각각이었고 목차도 매번 새로 짰다.
사용자가 "보고서 체계를 먼저 정리하자" 고 했다(2026-09-26).
이 스킬은 보고서 종류와 종류별 목차를 고정한다. 다음 보고서는 목차를 고르는 데서 시작한다.

## 좋은 보고서의 요소

출처는 클라우다이크 블로그 「보고서 작성이 막막하다면? 잘 쓰는 방법부터 공유 팁까지」(2024-12-19,
https://cloudike.kr/blog/ 보고서-작성이-막막하다면-잘-쓰는-방법부터-공유-팁/) 이다. 2026-09-26 에 열어 확인했다.

| 요소 | 쓰는 방식 |
|---|---|
| 명확한 제목 | 제목은 명사구 하나. 날짜는 제목 아래 첫 줄에 |
| 목적과 배경 | 1절 개요에 두세 문장. 누가 왜 요청했는지 |
| 목차 | 절이 다섯 개를 넘으면 제목 아래에 목차를 둔다 |
| 요약 | 개요 끝에 결론을 두세 문장으로. 바쁜 사람은 여기까지만 읽는다. 표는 결론 절에만 |
| 데이터와 사례 | 수치는 출처와 함께. 출처 없는 일반 지식은 "일반적으로 알려진 바" 로 표시 |
| 결론과 제안 | 끝의 결론 절에 요약과 옵션·제안 표를 한 번만. 그 뒤에 회의에서 정할 것 |

읽는 사람을 먼저 정한다. 처음 적용한 곳의 독자는 모임 운영진 네 명이었고, 회의에서 결정하는 데 썼다.
그래서 결론과 선택지가 앞에 오고 근거는 뒤에 둔다.

가독성은 세 가지로 챙긴다. 목록과 번호로 나눈다. 비교는 표로 한다. 문장은 짧게 쓴다.

## 쓰는 순서

1. 요청을 보고 아래 종류 중 하나를 고른다. 애매하면 검토 보고서다.
2. 그 종류의 목차를 복사해 제목만 채운다. 비어 있는 목차가 계획이다.
3. 자료를 먼저 모은다. 조사가 필요하면 서브에이전트에 맡기고 초안 파일을 받는다.
4. 초안을 끝까지 쓴다. 완벽하게 쓰려고 멈추지 않는다.
5. 절마다 추천 문장이 있는지, 결론 절의 옵션·제안 표가 모든 주제를 덮는지 본다. 같은 내용이 두 번 나오면 하나를 지운다.
6. `plain-writing/scripts/check_tone.py` 로 문장을 검사하고 고친다.
7. 출처 절에 실제로 연 페이지만 남긴다. 확인하지 못한 수치는 본문에 그렇게 적는다.
8. 보고서 폴더에 버전을 붙여 저장하고 진행 기록의 상태 표에 경로를 적는다.
9. docx 가 필요하면 `python <스킬>/scripts/md2docx.py <md> [docx]` 로 바꾼다. pandoc 이 없어도 된다.

처음 한 번 `setup.ps1`(윈도) 또는 `setup.sh` 를 돌린다. python-docx 를 깐다.

## 피할 실수

- 긴 문장과 어려운 말
- 결정과 관계없는 내용
- 보고서마다 다른 형식. 목차는 아래 종류에서 고른다
- 검증하지 않은 데이터. 검색 요약만 본 수치는 쓰지 않는다

## 보고서 종류와 목차

모든 종류는 같은 머리와 같은 꼬리를 쓴다. 가운데 본문만 종류에 따라 다르다.

```markdown
# <제목>

<작성일> · <작성자> · <버전> · 보고서 종류 <A~H>

## 1. 개요
목적 한 문장. 배경 두세 문장. 결론 두세 문장.

... 종류별 본문 ...

## N. 결론
### 요약
두세 문장.
### 옵션과 제안
| 대상 | 옵션 | 제안 |

## N+1. 회의에서 정할 것      체크리스트 (필요할 때만)
## N+2. 출처
```

본문의 각 절은 표와 근거를 보이고 "추천은 X 다" 한두 문장으로 닫는다. 절마다 요약·옵션·제안 소제목을 달지 않는다.
옵션과 제안은 결론 절의 표 한 곳에 모은다. 대상이 하나뿐이면 표 대신 문장으로 쓴다.

### A. 검토 보고서

방향이나 방식이 맞는지 따져 본다. 예: 설계 문서 검토 보고서.

```
2. 검토 기준            무엇을 기준으로 판단하는가
3. 주제별 검토          주제마다 한 절. 현황, 문제, 판단, 추천 문장
4. 결론
5. 회의에서 정할 것
6. 출처
```

### B. 비교·선정 보고서

후보 여럿 중 하나를 고른다. 예: 기술 스택, 디스코드 연동 방식.

```
2. 평가 기준            기준과 평점 척도(별 ½~5), 가중치가 있으면 적는다
3. 후보 목록            후보와 현재 상태(버전, 날짜)
4. 항목별 비교          항목마다 한 절. 후보 | 평점 | 성능 우위 | 구현 우위 | 특징, 추천 문장
5. 조합 비교            항목이 서로 얽히면 조합표와 평균
6. 결론
7. 회의에서 정할 것
8. 출처
```

평점은 대상 프로젝트에 맞는 정도다. 일반적인 우열이 아니다. 척도는 `★★★★½ (4.5)` 처럼 별과 숫자를 함께 쓴다.
평균 같은 계산값은 적은 뒤 다시 계산해 확인한다(v1.0.0 에서 틀린 적이 있다).

### C. 조사 보고서

사실과 평가를 모은다. 예: 웹앱에 대한 세간의 평가, 일정 입력 심리.

```
2. 조사 범위와 방법      무엇을 어디서 찾았나. 연 페이지 수
3. 발견 사항            주제마다 한 절. 데이터 표
4. 근거와 의견의 구분    데이터로 확인됨 / 반복된 의견 / 규범적 주장 / 찾지 못한 것
5. 대상 프로젝트에 대입  조건별로 해당하는지
6. 결론                한계(근거가 약한 곳)도 요약에 한 줄
7. 출처
```

### D. 회의 안건

회의 전에 돌린다. 예: 설계 확정 회의 안건. 안건 자체가 옵션과 추천이므로 결론 절을 따로 두지 않는다.

```
2. 회의 전에 확인할 사실  누가 무엇을 가져오나
3. 결정 안건            안건마다 옵션 표와 추천, 근거 보고서 위치
4. 세부 규칙            한 줄로 답할 것들
5. 검토만 받을 것        이미 적힌 값. 반대가 없으면 그대로
6. 회의 뒤 할 일         체크리스트. 담당과 기한
7. 참고 자료
```

### E. 회의 결과 보고

회의 직후에 쓴다. 회의록을 겸한다. 결정이 곧 결론이므로 결론 절을 따로 두지 않는다.

```
2. 일시와 참석자
3. 결정 사항            결정 | 근거 | 바뀌는 문서
4. 보류한 것            이유와 다시 볼 시점
5. 할 일               체크리스트. 담당과 기한
6. 다음 회의
```

결정은 근거와 함께 적는다. 결론만 남기면 나중에 번복할지 판단할 수 없다.

### F. 진행 보고

주간 점검에 쓴다.

```
2. 이번 주 요약          WBS 진척률, 한 문장
3. 완료한 것
4. 진행 중인 것          예상 완료일
5. 지연과 위험          원인과 대응
6. 다음 주 계획
7. 결론                지연 대응의 옵션과 제안. 없으면 생략
8. 요청 사항            누구에게 무엇을
```

### G. 결과 보고

작업이나 테스트를 끝내고 쓴다. 예: 테스트 결과서, 배포 결과.

```
2. 수행한 것            무엇을 언제 어떤 환경에서
3. 결과                표와 캡처. 캡처가 나온 시험은 캡처 필수
4. 문제와 조치
5. 결론
```

### H. 회고 보고

단계가 끝나면 쓴다. 예: 1차 회고.

```
2. 목표와 결과          목표 | 달성 기준 | 결과
3. 잘된 것
4. 문제와 원인
5. 결론                개선안이 옵션과 제안이 된다
6. 다음 범위
```
